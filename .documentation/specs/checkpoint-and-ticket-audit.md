# Checkpoint and ticket-audit

Two skills in the ele plugin: checkpoint reviews work before it is reported done or committed, and ticket-audit audits a tracker's ticket map against the code. Every script either runs is an `ele checkpoint` or `ele ticket` subcommand.

## Ticket-audit

- Ledger, `~/.claude/logs/ticket-audits.jsonl`: a record, never a scope. One line per item per audit: its key, its text hash, the methods that reached it, the user's rulings on its findings. Nothing in it skips a method or hides a finding; a later audit re-raises a ruled finding with the ruling attached, labelled text unchanged or changed since
  - Key: a ticket's `repo#number`; a plan item's repository, plan path and name, so a reworded item keeps its rulings; an unnamed item's checkbox text, normalised with the marker stripped, so rewording one loses them
  - Hash: a ticket's title, body and comments, since §9 records decisions as notes; a plan item's checkbox line and sub-bullets, marker stripped, so a tick is no change
  - `ele ticket corpus` writes `manifest.json` beside the corpus, key, hash and file per item, and takes `--plan <path>`, repeatable, one file per item, `<plan>-<nn>.md`, refusing two plans of one file name. `ele ticket ledger record` appends at the end of the report, copying the hash from the manifest the audit read, and refuses a key not in it or a method outside §3–§8
  - A ruling on one item's finding goes in the ledger; a decision that would outlive the item is an ele note
  - A ruling that commits the item to an edit not made in this audit is also drafted onto the item, since the builder reads the item, never the ledger: a note on a ticket, a `next:` line in a plan item's body
  - `/ele:ticket-claims` adjudications stay out: "dead" and "still true" are claims about code
- Corpus, `ele ticket corpus`: fetches in parallel; warns on a child holding a literal `Part of #MAP`; names no closed child in its `note:` lines; prints a blocker table that ignores prose after "Blocked by"; compares read-backs without the title line and trailing newline, against the body or with `--note` a comment, never both, so a note quoting a body edit cannot pass for it
- `/ele:ticket-claims` (`ele ticket claims`) checks `execution-map` and `typed-as-task`
- Errors: `plugin/reference/errors.md`, as in Checkpoint's Errors line; ticket-audit adds no rows
- Plans: `ele:plan-audit` audits them on ticket-audit's engine, an item standing for a ticket; ticket-audit keeps tracker maps only. The plan audit and the plan format are claude-ephant's design spec, Plans section

## Checkpoint

- Mode is small or full by size; scope is uncommitted, delta or branch
  - Record keeps a copy of each reviewed file in `~/.claude/cache/checkpoint-reviewed/`, never in the repository's `.git`
  - Delta is the freeze's call: whenever a record holds a path on the change list, each path diffs against its reviewed copy, or HEAD where there is none, and the delta's size picks the mode
  - Branch diffs against the merge-base with `@{upstream}`, else `origin/HEAD`, and refuses with neither. Run when asked; offered on a clean tree holding unpushed commits. Writes no delta: no record's copies describe commits
- A run opens with a freeze passing `--start`, or any freeze when none is open, and holds the re-freezes inside it. Each freeze replaces the run's frozen paths, and `--start` resets its clock, so a run abandoned without record or close inside the 120-minute window leaves the next run neither its paths nor its start
- A run's markers, open, frozen paths and start time, are per session and repository, so two sessions checkpointing one repository neither close nor time each other's runs; the record of reviewed bytes stays per repository, since identical bytes were reviewed whichever session asks. A freeze starts a run's clock only with `--start` or when none is running, and `log` or `close` stops it
- Errors: one shared `plugin/reference/errors.md` holds the retry rule (quote the error, one fix, one retry that never repeats the call unchanged, none where the row rules a retry out, then stop and report where the caller's instructions put errors) and the general rows, shell and guard-hook errors every skill hits: four per-skill copies had drifted. Checkpoint's SKILL.md keeps a local table of the rows only it hits (`not covered` from `check`, agent type not found, `command not found` in a §2 check); ticket-audit points at the shared file; reviewers read it through the brief's Errors field, since they read only what the brief names, and put an uncleared error under Questions. The guard-hook rows stay general, though only a user with those hooks meets them: a row fires only on its exact error text. No seen counts in the tables: they change nothing the agent does. The rows are drawn from `ele events --during <skill> --kind tool-error`
  - Not doing: a digest of each Bash call's full command, to tell a rerun among commands cut at 300 characters: the tables shipped without it
- SKILL.md size, in both skills: no line-count target. SKILL.md keeps what every run needs; a case only some runs meet sits in a file beside it, read when it arises: checkpoint's `BRANCH.md`, `DELTA.md`, `HEAD-EXPORT.md` and `PLAN.md`, ticket-audit's `TRACKERS.md`
- Plans: when a change completes the active ele plan's item, checkpoint proposes its tick with an evidence line saying what was asserted and at which commit; otherwise a dated progress line under the item. Written on approval
- Spec reviewer, `reviewers/spec.md` as `ele:checkpoint-reviewer`, only when the brief quotes a plan item or fetched ticket: a third parallel reviewer in full mode, a file added to the single reviewer's list in small mode. It reports what the item asked that is missing or partial, what is done wrong, and what the diff does unasked, each quoting the item's words, in its own section, unranked against the others. The brief says which requirements the change sets out to deliver, and an Observed field names what was run or measured toward the item, since the diff cannot show it. Its findings go through Verify: a missing requirement outside what the change sets out to deliver is logged `deliberate` and left to the plan's `next:` line, a confirmed unasked change goes to the user rather than being reverted, and any confirmed spec finding left unfixed turns the plan tick into a progress line. A missing requirement falls on no line, so delta scope does not drop it. The re-review gets the quoted item, what the change sets out to deliver and the Observed field
- A test is never changed to pass: the session making the gate green is the likeliest to change one. Verify and Gate fix a red test in the code, and change what a test asserts only for a behaviour change the work sets out to make, which the report names; a rename or signature change edits a test without changing what it asserts, so the rule is on assertions, not on any test edit. `reviewers/bugs.md` reports an expected value rewritten to the code's output, a weakened assertion, a widened tolerance, or a skipped or deleted case with no such behaviour change, so `/ele:review`'s bugs reviewer, reading the same file, reports it too
- Log, `~/.claude/logs/checkpoints.jsonl`. Fields: `mode`, `scope`, `severity` per finding (blocker, defect, quality, nit), `also_raised_by` per finding, so a merged duplicate still counts its reviewers, and `duration` per run, in seconds from the first freeze to the log line. `/ele:checkpoint-stats` reports each. Review runs share the log with their own scopes, `mr` and `local-branch`, and fields, `target`, `reviewed`, `dropped`, the verdict `confirmed` and a per-finding `outcome`, and mode `full`, with no `mutations`, `rereview` or `duration`. `log` refuses `target`, `reviewed`, `dropped`, `outcome` and `confirmed` on a checkpoint, and `mutations` and `rereview` on a review; stats report review runs in their own section, with the skip rate and the dropped counts, since review's severity definitions are wider
- Cost, measured with ele's usage report. Reviews stay in subagents, since inline they would grow the parent's context for every later turn, but cheaper ones:
  - Prose and conventions are one reviewer, reporting under both labels so the Stop hook and the stats sources are unchanged
  - An `ele:checkpoint-reviewer` agent type on sonnet, without the Skill tool, runs it and the re-review; the bugs reviewer and the small-mode reviewer stay on the session's model. As of 2026-10-16 an agent type without the Skill tool receives no skill list
  - Not doing: dropping the `ele recall` fallback from checkpoint §2 and ticket-audit §0: a skill run inside a subagent gets no skill list, so the recall skill they would otherwise point at is not there
  - Small mode up to 40 lines, 100 for Markdown or text. The bar is a judgment, not a measurement

## In the plugin

Checkpoint and ticket-audit ship in the ele plugin: `claude plugin eval` needs a plugin; hooks, scripts, skills and agent type ship and version together; one language. The plugin needs no file outside itself and the ele binary, and names its prerequisites.

- Prerequisites: in the [README](../../README.md). ele on `PATH` is a hard one, since the plugin's hooks call it
- The checkpoint gate, the Stop hook's block and the prompt hook's snapshot, is ele's option `checkpoint_gate`, on by default; with it `false` both hooks only clear the session's baseline, so turning it back on starts from the next prompt, and a `config.json` that does not parse leaves the gate on. Claude Code cannot turn off one hook of a plugin
- The convention files in the brief are the user's `CLAUDE.md`, under `$CLAUDE_CONFIG_DIR` when set, else `~/.claude`, with what it imports or says to read, and the repository's; the prose reviewer's per-comment tests apply where those hold no comment rules
- In the plugin: the `checkpoint` skill with its reviewer files, the `ticket-audit` skill, the `checkpoint-reviewer` agent, addressed as `ele:checkpoint-reviewer`, and `/ele:checkpoint-stats` and `/ele:ticket-claims` in `commands/`
- Subcommands, grouped as `plan`, `owner` and `handoff` are: `ele checkpoint base|check|close|density|freeze|hash|log|optout|record|stats`, `ele checkpoint gate` (Stop) and `ele checkpoint snapshot` (UserPromptSubmit), and `ele ticket claims|corpus|ledger`; shared state and hook logging are code in `internal/checkpoint`
- The Stop hook's block reads "no checkpoint was reported" word for word, since mining and hook-log readers match it, and names `ele:checkpoint` and `ele checkpoint optout`. Its `Changed:` line lists the paths space-separated, since `ele events --kind hook-block` reads them as `changed` and judges each block by them, with `checkpointed`, `reply` and `disputed`, as design.md's Events section says; `ele show <session> --at <time>` opens a block's turn. ele writes its own hook-log lines, to `~/.claude/logs/hooks-<YYYY-MM>.log` in the format the user's other hooks write, so the plugin depends on no file outside itself
- Contract kept: log formats, and the `reviewers/<name>.md` layout ele's mining reads. Mining matches runs by the old bare names as well as the `ele:` ones, since transcripts from before the skills moved into the plugin keep the old names; the Stop gate and stop-check accept the bare `checkpoint` name too, for a session resumed from before the move
- `task eval` runs the plugin's `claude plugin eval` cases, `plugin/evals/`, against the installed plugin or a path
