# Stop check

## Why

- Without it, notes are proposed unasked only at a checkpoint, so sessions that never reach one (investigations, debugging, questions) never prompt for notes
- Agents print `ele remember …` commands for the user to run instead of asking with AskUserQuestion and writing the note themselves, which the remember skill's Propose section requires
- Nothing stops a session growing: as of 2026-10-19 sessions run with the 1M window, whose auto-compact fires near 967k, and only the user can run `/compact`; no hook output, tool or skill triggers it

## Hook

`ele stop-check` is a `Stop` hook in `plugin/hooks/hooks.json`, run as `ele stop-check || exit 1`.

- Input: stdin JSON with `session_id`, `transcript_path`, `cwd`, `stop_hook_active`
- Exits 0 silently when `cwd` has no owner. `stop_hook_active` true suppresses the block only; a message cannot loop

## What it reads

The transcript, through `internal/transcript`, for:

- Work done since the last block or proposal: Edit / Write / NotebookEdit, or a Bash call other than a read, since a command can change files, and a wrong `/clear` mid-task loses more than a wrong `/compact`
  - A read: every simple command in it, pipelines, chains, loops and `$( )` bodies included, is a listed read (`grep`, `cat`, `ls`, `sed` whose script only prints, deletes, quits or substitutes without `w` or `e`, `find` without `-exec` or `-delete`, `git log`/`status`/`show`/`diff` without `--output` and the like) or ele's own read or bookkeeping (`ele plan show|check|list`, `ele recall`, `ele reminder list|close|reopen`, `ele handoff list|close|reopen`, `ele context`, `ele flag`, `ele checkpoint base|check|density|hash|stats`, `ele checkpoint record|log`, which write only ele's data directory, `ele config get|list`, `ele show`, `ele events`, `ele stats`, `ele status`, `ele usage`, `ele version`, and any `ele` command whose first flag is `--help`), with no assignment prefix on a command and no `git -c`, `rg --pre` or `sort --compress-program`, and it redirects only to `/dev/null`, a file descriptor or a path under `/tmp/` or `/private/tmp/`
  - A heredoc whose delimiter is a quoted plain name, `<<'EOF'` or `<<"EOF"`, keeps its body literal, so the body is stdin, not commands, and the command it feeds is judged as any other: `ele checkpoint log "$R" <<'EOF'` reads, `sh <<'EOF'` and `cat <<'EOF' > x.go` are work. It reads only when the command up to the end of the heredoc's line holds no `\`, backtick, bracket, brace or parenthesis, no quote left open on its line and no `$` but one starting a plain variable, so that line's newline is where the shell's body starts too: each of `\`, a quote spanning lines, `${`, `$[`, `$'`, `((` and zsh's `=(` can carry a line past its newline or hide a `<<` from the scan, and reading every such form takes a shell parser. A line after the closing delimiter line runs as a command. Any other heredoc, an unquoted delimiter's, whose body expands, a here-string, and anything else it cannot read whole, such as an unclosed quote, is work. A `$'…'` quote is read with its backslash escapes, so `\'` does not end it. A `$(cat <<'EOF' … EOF)` substitution, the usual way to pass a multi-line note, reads the same way
  - Read from the call's whole command, since the indexed text collapses whitespace and is cut at 300 characters
  - Neither work nor mid-task: a proposal's own calls, after a proposal or a remember block until the next prompt, so `ele:wrap`'s reads do not re-pend the notes it just proposed. An `ele:recipe` or `ele:write-report` run's own calls are exempt the same way, but neither is a proposal: work before it stays pending for the next notes ask
  - The rules are pinned in tests
- An AskUserQuestion call: work for the notes ask but not for mid-task, since a session that only decides is the one most worth notes, and a question changes no files. Not work while a checkpoint or a review runs, as nothing then is. Not work after a remember block or a proposal, until the next prompt: that question asks the proposal's own notes, and counted, skipping every note would ask again. A declined question still counts, so tool results are never parsed
- A subagent's Edit / Write / NotebookEdit calls, read from its transcript in `<session>/subagents/agent-*.jsonl` beside the session's transcript, since Claude Code keeps them out of the parent transcript: work for both the notes ask and mid-task. Not its Bash. Subagent transcripts are read after the session's, so each edit is placed by its line's timestamp. One stamped before the last notes proposal, a proposal skill or an `ele remember` command, or before the last notes ask, is not work: the proposal or the ask covered it, though read after it. One stamped before the last checkpoint's start is not mid-task, whether read while that checkpoint runs or after it: the checkpoint cleared it, as it clears the parent's work, and a scan behind on its budget, or the first stop after an Esc, reads it only once the next prompt has ended the checkpoint. Any other edit stamped before the last proposal is mid-task outside a checkpoint and not while one runs. Any other edit is work outside a checkpoint, even while a proposal runs, its exemption being for its own calls, and no proposal skill launches an editing subagent. While a checkpoint runs, it is work only if not stamped after the checkpoint started, and then not mid-task, as for the parent: its reviewers are not work, and an edit delegated just before it is. An edit with no timestamp, or one equal to the checkpoint's start or the proposal's, is not placed before either, so is work unless stamped after a running checkpoint's start: a doubtful edit costs one more ask rather than dropping work. A stop not behind reads each subagent file on from its saved offset, from its start where it has none, so an edit before the session's first stop is asked about
- A turn ended by Esc fires no Stop, so its lines, subagent edits included, are read no earlier than the first stop after the next prompt: as of 2026-11-16, Claude Code 2.1.311, interactive, a Stop hook appending a marker per firing logged none for a turn interrupted while its text streamed or while a Bash call ran, the terminal showing that call interrupted, each transcript holding `[Request interrupted by user]`, or `… for tool use]`, and no `stop_hook_summary`; an uninterrupted turn in the same sessions logged one
- Notes proposed, which clears the work before it: the `ele:remember`, `ele:handoff` or `ele:wrap` skill ran, or a command starting `ele remember` did, other than `ele remember --help`, a help lookup and so a read; leading `cd <dir>;` or `cd <dir> &&` aside, its other simple commands still judged as work or read outside a checkpoint or proposal, so a write chained after the note counts and a read marks the session mid-task
- Nothing while a review runs, from the launch of its first `ele:review-reader` agent until its log line, a command starting `ele checkpoint log` (a leading `cd <dir>;` or `cd <dir> &&` allowed), or until a checkpoint starts: the review's turns end while its readers run and when a Raw Markdown answer is printed as plain text, the user's next message resuming it, so its stretch outlives prompts, and a notes ask at any of those stops would interrupt it. It starts at the readers, not at `/ele:review`, since a run refused at its target logs nothing and would leave the stretch open; a run that launches its readers has saved its diff, and logs when it finishes or stops. Work pending before it stays pending for the first stop after it. A review abandoned after its readers launch, its log never run, leaves everything after it uncounted, for notes and mid-task alike, until a checkpoint or `/clear`; that work is never asked about
- Work done since the last run of the `checkpoint` or `ele:checkpoint` skill, as a Skill call or a typed slash command, else since the session started, for mid-task. A question is not mid-task work, and a read is: `/clear` mid-investigation loses what the reads found
- Context size: `transcript.ContextTokens` of the last main-thread response, as `ele context --size` computes it
  - The last on disk when the hook reads, which can be the previous turn's: as of 2026-11-16, Claude Code 2.1.311, interactive, a Stop hook copying the transcript at each of four stops found every usage line of its turn on disk at three, and none at the fourth, its copy ending at the turn's `api-request` line, the reply arriving as the hook input's `last_assistant_message`. A turn read that way is judged at the previous turn's size, or at 0 with no hint and no error when it is the first, so a turn that crosses the threshold gets its hint one stop late: its band stays unhinted and the next stop hints
  - Not doing: waiting or retrying for a usage line not yet on disk: a wait slows every stop, and the next stop hints anyway

## Outputs

The two are decided independently; both can go out on one stop.

- Size hint: context ≥ threshold, the `compact_hint_at` option (default 150000; 0 turns the hint off and forgets the band hinted), in a band not yet hinted, band being `(context − threshold) / 100000` rounded down → `systemMessage` only, never a block, since a block costs another turn at full context
  - Mid-task, meaning work done since the last checkpoint: `Context <n>k. At a pause: /compact <focus>`, focus being the title of the lone active plan's next item, else a bare `/compact`. A plan stays active across sessions, so it alone is not mid-task
  - Otherwise: `Context <n>k. Wrap up (/ele:wrap), then /clear`, since wrap offers the handoff with the notes and reminders a session end needs
  - Not doing: running `/ele:wrap` from the hook: the hint names it and the user starts it
  - Not doing: holding a behind stop's hint until its scan catches up, though partial state can give `/compact` for an edit whose checkpoint the scan has not reached, and spend the band: it keeps the hint timely on a long transcript, where size matters most, and a wrong choice between `/compact` and wrap costs little
- Notes block: off, the `notes_ask` option drops unproposed work at each stop, so turning it on asks only for work done after. On, its default: work done since the last block or proposal, with no block yet in this stretch, no checkpoint or review running and `stop_hook_active` false → block with the remember reason. A stretch runs from one checkpoint to the next: nearly every turn runs work, so without it nearly every turn would block. A checkpoint starts a stretch but keeps unproposed work, so the first stop after it ends, at the next prompt, still asks unless notes were proposed since. Not while it runs: its turn can end with reviewers still out. A stretch also ends 60 minutes after its ask, on the hook's clock, so work since asks again: a session that never checkpoints again would otherwise never be asked again. Work since is what sets pending, an AskUserQuestion included, since an answered question is often a decision worth a note. The 60 minutes are fixed, with no option
  - Not doing: loading `config.json` only when the block asks for notes: a `config.json` that does not parse is worth hearing about every turn, and loading it less often hides the error
- Neither → exit 0

The remember reason: "This stretch's work has not been proposed as notes; /ele:remember's Propose section covers it: one Write/Skip question per note, at most four per AskUserQuestion call and as many calls as it takes, then each approved note written with ele remember, the command never printed for the user to run. With nothing worth keeping, one line says so." It restates the skill's per-call rule because a session can act on the reason without loading the skill. With `auto_note_writes` on, the reason says the notes are written without the question. It states facts, not orders: context worded as a system command can read to Claude as a prompt injection, which it then shows the user instead of acting on.

A block goes out as `hookSpecificOutput.additionalContext` with `hookEventName` `Stop`, never `decision: "block"`, which keeps the turn going the same way under the same loop guards but reaches the user labelled a hook error. As of 2026-11-03, Claude Code 2.1.308, a `decision: "block"` reason reached the model twice, as `Stop hook feedback:` and as `Stop hook blocking error from command: …`, and the additional context reaches it once, as `Stop hook additional context: …`. As of 2026-11-04, 2.1.308, interactive, the terminal shows the notes ask as `Stop hook feedback: <reason>` under the `Ran <n> stop hooks` line, with no error label. On 2.1.308 and 2.1.309 the transcript records it as a `hook_additional_context` attachment with `hookEvent` `Stop` and in `stop_hook_summary`'s `hookAdditionalContext`, with no feedback line. As of 2026-11-03 the Claude Code changelog adds it in 2.1.163; an older build is expected to ignore it, ending the turn unasked, not observed. Older builds do not get `decision: "block"` beside it: a newer build may still label the turn an error, unchecked, which would defeat the change. As of 2026-11-13, 2.1.311, in one headless run, two Stop hooks that both continue one stop each get their own attachment, holding that hook's text alone and not in settings order, so the notes ask's event keeps its own first line and the ask is counted.

## State

Per session, in the data directory: the transcript offset read so far, and each subagent transcript's, with the flags derived from them and the timestamps of the last checkpoint start, notes proposal and notes ask, the ask's in the transcript's form so a subagent edit's stamp compares with it, whether this stretch has blocked, and the highest band hinted, so each stop reads only new lines and each output fires at most once per stretch or band and never loops. A block suppressed by `stop_hook_active` stays pending. A state saved before the ask's time was kept, its stretch blocked, reads as asked at the first stop that loads it, so its hour runs from there.

A stop stops reading the transcript at the first line boundary after 10 seconds, a third of the hook's 30-second timeout, having read at least one line, then saves its offset. A hook killed by the timeout saves nothing, so an unbounded first scan of a long transcript would start over at every stop. Time rather than bytes, since a cold read is several times slower than a warm one. While a scan is behind, the stop holds the notes block, which stays pending, since a proposal not yet read may have cleared the work, and reads no subagent transcript, since their edits are placed against the parent's state. A stop not behind, the stop that catches up included, reads each subagent file on from its saved offset, and from its start where it has none: a first stop, or one whose transcript was replaced or whose state was removed or did not parse. That read keeps no deadline, and a stop the timeout kills there saves nothing, so the next repeats it on a warm cache: recording the files unread instead would never ask about an edit made before the first stop. The size hint still fires: its count is read from the tail. Context below the threshold resets the band, so a session that compacts and regrows is hinted again. Old state is cleaned up on sync.

## Replay

`ele stop-check --replay --since <time> [--until <time>]` runs the hook as built, its `advance`, `subagentEdit` and `rememberBlock`, over archived sessions, so a change to it is judged against real stops rather than reasoned about. Each stop is judged at its own timestamp, so a stretch's hour runs on the transcript's times as the live hook's runs on its clock, and the two judge alike; a stop with no parseable time neither starts an hour nor ends one. It reads each transcript whole, with no scan budget, so at a stop where the hook was still behind it can say `asks` where the hook held the block. A date bound reads from local midnight. It prints one JSON object per stop in the window, `--until` excluded: the session, owner and project, whether the notes ask fired there (`asked`), whether the hook as built would ask (`asks`), with the work kinds that set it pending (`trigger`: `edit`, `bash`, `question`, `subagent-edit`) or why it would not (`whyNot`), and how the stop was found (`stop`).

- Transcripts: each owned main transcript with an indexed line in the window, replayed whole, so a stretch or checkpoint begun before the window carries in, ordered by earliest indexed line. An unowned one is left out: the hook exits before judging it
- Stops, `recorded`: each `stop_hook_summary` line of the main thread. As of 2026-10-27 Claude Code writes one per Stop, after the hook's block feedback, and as of 2026-11-03, 2.1.309, after its additional context. A Stop whose hooks an Esc cancels writes none, so replay does not judge it: as of 2026-11-16, 2.1.311, an Esc during a turn's Stop hooks left a `hook_cancelled` attachment naming one of them, 0.16 s after the reply ended, then `[Request interrupted by user]`, though the probe's own Stop hook had run; whether `ele stop-check` finished was not seen. `asked` is a Stop hook block naming `ele:remember` since the previous one, read from a `Stop hook feedback:` line or from a Stop `hook_additional_context` attachment
- Stops, `placed`, for a transcript with no `stop_hook_summary` line, such as one older than them: a group of Stop hook blocks under 2 s apart with nothing between, before a prompt that follows output, and at the last line after output. A Stop that blocked nothing and preceded no prompt leaves no trace, so placed stops are approximate
- `stop_hook_active`: a Stop hook blocked since the last prompt. A block's feedback line parses as a prompt and the hook's state reads it as one, but it does not end that, a block group or output
- Subagent edits: the archived subagent transcripts' Edit / Write / NotebookEdit calls, each line counted once across generations, applied at the first stop at or after their stamp, since the hook reads subagent files after the transcript, from their start at a first stop, so edits up to a transcript's first judged stop, unstamped ones included, count there
- Resumed transcripts copy earlier lines, stops included, with their ids. The hook's state is per session, so a resumed one reads the copied lines in one pass at its first stop and judges nothing at the copied stops: the replay runs the copied lines through the state but judges a stop only once, in the transcript indexed first, which the index's own copy rule makes the original
- `whyNot`, first that holds: `hook-active`, `checkpoint`, `review` running; nothing pending after a proposal since the last stop, `proposal`, else `nothing-pending`; the stretch's ask spent, `stretch`
- Each stop is judged on what the session did. After a stop where the replay and the real hook differ, the session went on as it did, so a later stop can differ only because an earlier one did, such as an ask moved earlier spending the stretch

## Beside the checkpoint gate

- The checkpoint `Stop` hook, `ele checkpoint gate`, also blocks. Neither yields: both may block on one stop, and a remember block suppressed by `stop_hook_active` after a checkpoint block waits, like any pending work, for the first stop after the checkpoint ends
- The remember skill's Propose section is the single definition the hook points at, and never falls back to printing the commands
- The checkpoint skill's Notes step defers to the hook in one line, so nothing is proposed twice
