# claude-ephant design

Cross-session memory for Claude Code: ele archives every session's transcript, indexes it for search, keeps the decisions, questions and facts a user approves as notes, and shows the ones that matter at the start of each session.

## Principles

- No background LLM. The only model calls are `/ele:remember`, checkpoint proposals and `/ele:mine` classification, made inside the session already running, on that session's account
- `notes/`, `archive/`, `mining/` and `owner-map.json` are the source of truth. The database is a disposable index, rebuilt by `ele reindex`
- Nothing crosses owners unless asked
- A note records a decision, a question or a dated fact, never a description of the code. Code descriptions go stale; decisions and questions do not
- ele's skills put an idea taken from another plugin in their own words rather than call that plugin's skill: its names change between versions, as writing-great-skills became writing-for-agents

## Owners

One store. Every record carries an owner, whose work it is, and the profile that ran it, as a fact.

- Owner, not profile, scopes isolation: one owner's repositories can run in several profiles, so a profile does not separate one owner's work from another's
- Owners come from `owner-map.json` in the data dir, approved by hand: the list of owners, path rules, and per-project entries. Each entry's owner is resolved when it is indexed, so when the map's content changes the next sync rebuilds the whole index from the archive. Sync fingerprints the bytes it parsed, so a map written mid-sync triggers a rebuild at the next one
- `ele owner add <name>`, `add-path <dir> <owner>`, `add-project <name> <owner>`, `remove-path <dir>` and `remove-project <name>` edit the map, refusing an invalid name, a relative path, an unlisted owner or an absent rule. A replaced rule prints its old owner. Each prints the projects that change owner, from every (directory, project) pair the index has seen resolved under both maps; listing an owner counts, as it turns on rules already naming it. They hold the archive lock, refusing while a sync holds it or before one has completed under this index version. Notes filed under an owner that stops covering their project are refused, naming the count, unless `--move` refiles them under the single new owner, or `--move-to <owner>` under a listed owner when no single owner covers the project after the change. Forgotten notes count and move the same way, inside `forgotten/`. The map is written sorted and renamed into place, then a background sync starts unless `--no-sync`
- A project entry wins; otherwise the longest path rule containing the working directory decides. A live session matching neither has no owner: it is left out of default recall and the SessionStart block, which says so once and names `/ele:setup`
- `/ele:setup` is onboarding, after installing and in each new unowned repository: it reads `ele status`, and where no owner covers the directory, or a rule names an owner the map does not list, asks the user which owner, a listed one or a new name the user gives, and what to map: a path rule on the directory above the root, offered first so sibling repositories come too, unless that is the home directory or `/`; the root alone; or a project entry. Paths come from the directory `ele status` names, not from git, which resolves symlinks where path rules match the path as the shell reached it; a directory whose `pwd -P` differs gets each path rule in both forms. The root is the nearest directory holding `.git`, as `GitRoot` in `internal/index` finds it; in a worktree the first option is the directory above the main checkout, since the one above a worktree holds only worktrees. The user approves each mapping, as with every other write to the map. On approval it runs the `ele owner` commands, every one but the last with `--no-sync`, since each write starts a background sync whose lock refuses the next write; a write refused over the lock or an unfinished index is retried once after a foreground `ele sync`, which waits for the lock, run with the Bash tool's longest timeout since a first sync can take minutes. It ends with `ele status` naming the owner, and runs no `ele sync` of its own: the last write's background sync files existing sessions under the new map, or `ele sync --background` does when the last write changed nothing
- `/ele:recall` searches the current owner, or the owner of the project `--project` names. `--owner <name>` or `--all` reaches others
- The SessionStart block never crosses owners
- Profile: `CLAUDE_CONFIG_DIR` unset is `claude`, `~/.claude-<name>` is `<name>`. For history, the profile directory holding the transcript, or empty when no transcript survives

## Transcripts

- Each profile's `projects/`, subagent transcripts included and tagged
- Archived verbatim and compressed under `archive/transcripts/<profile>/`, mirroring the path within `projects/`. Only appended to, apart from rolling back an append the manifest never recorded: each sync adds a gzip member holding the new complete lines, and a new file is written under a temporary name and renamed into place. As of 2026-10-15 Claude Code deletes transcripts older than its `cleanupPeriodDays` setting, so the archive keeps what it deletes
- `archive/transcripts/manifest.json` records, per file, the generation, archived offset, archive file's size and a hash of up to 4 KiB before the offset. A source whose hash no longer matches was rewritten in place and starts a new generation file (`<name>.g<n>.jsonl.gz`); an append to a recorded file that the manifest never saved is truncated on the next sync
- Indexed: what the user typed, assistant text, and one line per tool call: the tool name plus its primary input (command, path, pattern, query, url, skill…; else the input as JSON), capped at 300 characters. Tool output, thinking and compaction summaries are not indexed, nor are user-role lines whose origin is not human, or that carry no origin and open with a harness tag. A subagent's user lines, its parent agent's brief, are indexed as conversation, not as prompts. A "You should know" note the user sent is indexed as kind `heads-up`: a typed line starting `✦ Heads up ·`, or, as of 2026-10-29 as Chat in main session sends it, `Here is a note offered by a side agent:`, a blank line and `> Heads up ·`. Claude Code writes it as it does a typed prompt, so the text is its only mark, and a line with typed text before the mark stays a prompt. An index built before the kind existed holds another `index-version`, so the first sync after the upgrade rebuilds it and reclassifies earlier heads-ups. It starts a turn as a prompt does, so the Stop hook, `ele events` and `ele usage` count it as one; recall ranks it with conversation, as Claude wrote it. A note shown and never sent is in no transcript and is not indexed
- Sessions from an SDK entrypoint (`sdk-*`) are archived but not indexed, whoever started them, so a plugin's automated runs do not flood recall; a user's own SDK runs are left out too
- Entries are keyed by their line's id and place on that line, so a line indexed once is never indexed again: a transcript rewritten in place and archived again from its start adds no entry twice, and a line Claude Code copies into another transcript, as a resumed, forked or subagent session does, keeps the copy indexed first: usually the parent's, but the first file in walk order when one sync archives both, as a rebuild does. Lines without an id are not deduplicated
- An entry's project is the basename of the git root above its `cwd`, or of the `cwd` itself when none is found; its owner resolved through `owner-map.json`

## Sync

`ele sync` is incremental and idempotent: copies new or grown transcripts, indexes from the last byte offset, re-indexes changed notes. One advisory file lock on `archive/transcripts/` serialises `ele sync`'s archive and index writes.

Triggered by:

- SessionStart hook, in the background
- SessionEnd hook, in the background
- `/ele:recall`, before searching

Each successful sync writes a stamp. The SessionStart block warns only when the stamp is missing, malformed or more than a day old, naming `sync.log`, which collects the output of background syncs, newest last.

A rebuild drops and recreates the index's tables, keeping only its settings. Sync rebuilds when the owner map changes, when the index holds another `index-version`, or none after a completed sync, and when a table this build creates is missing or has other columns or another definition; a table only the index has is left alone. Opening the index compares its tables first and applies the schema only to a new index or a matching one, so a schema change shipped without a version bump, whether an added table, an added column with any index on it, or a changed constraint, is rebuilt rather than failing every sync. The settings table is left out of the comparison, since a rebuild keeps it. Every other reader refuses an index whose tables differ, naming each difference and saying to run `ele sync` to rebuild it: `recall`, `show`, `events`, `stats` and `remember`'s owner lookup fail with it, and the SessionStart block shows it in place of the session count.

The `index-version` setting makes the first sync after an upgrade that changes what is indexed rebuild the index, so history gets the new rows too; an index with no owner-map fingerprint either is new and is built, not rebuilt.

## Notes

- Written by `/ele:remember` or `/ele:handoff`, or proposed when ele's Stop hook asks, and written on approval; a `plan` note only by `ele plan start` and a `flag` note only by `ele flag`, which `ele remember` points to
- `/ele:remember`'s Propose asks one Write/Skip question per note, at most four per AskUserQuestion call, the tool's limit, and as many calls as it takes, so no note is dropped
- With `auto_note_writes` on, a note proposed through `/ele:remember`'s Propose section, whether the Stop hook or a skill asks, is written without the Write/Skip question and reported with its id and words, a handoff or a superseding note included: one rule for every proposer, and the id lets a wrong one be forgotten. The Stop hook's block reason says which applies; the skill reads `ele config get auto_note_writes`
- One Markdown file per note: `notes/<owner>/<id>.md`; an everywhere note under `notes/_all/`, a folder no owner can take, since an owner name starts with a letter or digit
- Front matter: `date`, `kind` (`decision` | `fact` | `flag` | `handoff` | `plan` | `question` | `reminder`), `owner`, `scope` (`project` | `global` | `everywhere`), and `project` when the scope is a project; owner `_all` with scope `everywhere` and neither without the other; `due` (YYYY-MM-DD, or YYYY-MM-DDTHH:MM, both local) on a reminder and only there; optional `closed`, `done-file` and `every`, on a reminder and only there (`closed`: when `ele reminder close` closed it, RFC 3339 UTC; `ele reminder reopen` removes it. `every`: a nudge's interval, a bare whole number of days above 0, or minutes or hours as `5m` or `2h`; whole days are written bare so a build that reads only days still reads every day nudge, and one before sub-day intervals counts a `5m` note, or a due with a time, invalid. A due with a time is fixed width, a zero-padded hour, as the string comparison needs. `done-file`: an absolute path, only with `every`), `profile`, `session`, `shown` (when the start block showed a lone handoff, `ele handoff close` closed one or `ele plan done` closed a plan, RFC 3339 UTC; `ele handoff reopen` removes it), `supersedes`, `time` (when it was written, RFC 3339 UTC; `ele remember` sets it), `verdict` (`good` | `bad`, on a flag and only there). A flag, handoff or plan is scoped to its project; a flag needs a `session` and `time`, where `time` is the moment it marks rather than when it was written
- Body: one to three lines, reason inline; `ele remember` refuses more
- `ele remember` takes owner and project from the working directory, refusing one no owner covers unless `--owner` names one; profile from `CLAUDE_CONFIG_DIR` and session from `--session`, else `CLAUDE_CODE_SESSION_ID`; `--session ""` files none. `--project` names the project instead, so the command works from any directory; its owner comes from the project's entry in `owner-map.json`, else from the index when exactly one listed owner has entries for it and the index was synced under the current map, else `--owner` is required. `--project` refuses surrounding spaces and control characters; `--owner` names a listed owner and overrides the lookup; `--supersedes`, repeatable, names notes of the same owner, each once. A note whose text, whitespace aside, matches an unsuperseded note of the same owner, kind and scope, and project when project-scoped, is refused, naming that note; a closed handoff or reminder does not count, so the same words may be saved again; a nudge never closes, so its words are refused while it lives. A reminder's due date is not compared: the same words at another date are the same reminder moved, re-dated with `--supersedes`. `--due <YYYY-MM-DD[THH:MM]>` is required on a reminder, today by default with `--every <interval>`; `--every` and `--done-file <path>`, stored absolute and only with `--every`, make it a nudge; all three are refused on any other kind. `--everywhere` files the note under `_all` with no project, needs no owner to cover the directory, and is refused with `--global`, `--owner`, `--project` or on a handoff; its duplicate check and `--supersedes` read only everywhere notes, so one note never supersedes across owners
  - Not doing: a repo-trait key on the `everywhere` scope, such as every Go repo: trait detection is its own design, which traits, detected how and cached where, and nothing needs it yet
- No `ele` command edits a note in place: rewording supersedes. `ele forget [--owner <name>] <id>...` moves mistaken notes from `notes/<owner>/` to `forgotten/<owner>/`, which sync does not read, an everywhere note from `notes/_all/` to `forgotten/_all/`, and from a directory no owner covers only everywhere notes, checking every id and destination first and refusing one a live note supersedes; it says when a note the forgotten one superseded has no live supersessor left. `--restore` moves them back, refusing one a live note, or another note in the same call, already says, as `ele remember` would
- The file name is the id; `ele` names files `<YYYYMMDD>-<6 hex>`. `supersedes` names other notes' ids, comma-separated
- A superseded note stays searchable and is shown as superseded by the successor with the lowest id. A note naming a missing id supersedes nothing
- Notes are hand-editable. `ele sync` drops notes whose files are gone, then re-indexes those whose files changed, so a note moved between owner folders is not rejected as a duplicate of itself. Symlinked note files are skipped. A note is left out of the index and named in the sync output when its first line is not `---`, its front matter never closes or has a line that is not `key: value`, a key is unknown or repeated, the date is not YYYY-MM-DD, the kind or scope is outside its set, the owner or body is missing, the id is empty, a project scope has no project, the owner differs from its folder, an `everywhere` scope and owner `_all` do not come together, the session holds anything other than letters, digits, `-` and `_`, the project holds a control character, a flag, handoff or plan is not project-scoped, a flag lacks a session, a time or a verdict of `good` or `bad`, another kind carries a verdict, a plan's body is not one relative path inside the project, `shown` or `time` is not RFC 3339, it supersedes itself or names an id twice, or its id is already used
- Recall shows each note without a session under its own heading
- `ele context [--owner <name>] [--project <name>]` prints every live note for a project, the owner's global notes and the everywhere notes — open questions, then decisions and facts, newest first, superseded ones left out — with no budget, for a reader that needs all of what is settled, then every handoff the next startup or `/clear` would show, newest first. Owner resolution and its refusals are `ele remember`'s
- `ele flag good|bad [--owner <name>] [--project <name>] [--session <id>] <why>` saves a `flag` note stamping a session moment with a verdict and the reason, for a later study of sessions; `/ele:flag good|bad <why>` runs it with the user's asking as the approval, and `/ele:flag list` shows `ele flag list`. The verdict is a front matter key, not a word in the body, so a reader filters on it without parsing prose. The session is the running one from `CLAUDE_CODE_SESSION_ID`, refused when there is none; `--session` names an earlier one by id or prefix and must resolve to exactly one indexed session, since a hand-typed id with a typo or a shared prefix would stamp a flag nobody can open. The `time` is the moment marked, not when the note was written: now for the running session; for `--session`, the timestamp of the indexed entry at or after `--at <time>` (RFC 3339, any offset, refused outside the session's first and last entries, and refused without `--session`), else of the session's last entry. Saving the time it was given would put a flag given afterwards past the session's end, and storing an entry's own timestamp, not the time typed, lets `ele show <session> --at <time>` compare it as a string and land on that entry. `ele show --note` anchors on a note's words, not its time, so `ele flag list` prints the time and points at `ele show --at` instead. Owner and project resolve as `ele remember`'s; the body is one to three lines; no duplicate check, on saving or on `ele forget --restore`, since each flag marks its own moment. Flags never show in the start block or `ele context`: they are for later study, not for the next session. `ele flag list [--owner <name>] [--project <name>]` lists the project's unsuperseded flags newest first, each with its verdict, time, session prefix, id and body redacted on one line. `ele flag` counts as ele's bookkeeping, not work, for the Stop hook's notes ask. A build before the `flag` kind reads a flag note as invalid and leaves it out of the index
  - Not doing: a `flagged` mining analysis digesting each flag's moment: the self-audit reads flags
- `ele context --size` prints the running session's context in tokens: input, cache write, cache read and output of the newest main-thread response with usage, read from the live transcript, since a sync can be a session behind. The session comes from `CLAUDE_CODE_SESSION_ID`
- `ele reindex` empties the index and rebuilds it from `archive/`, `notes/` and `owner-map.json`
- Project is the git root of the working directory, or the directory itself outside a repo

## SessionStart injection

`ele session-start` prints it, then starts `ele sync` in the background. Owner and project come from the working directory; as of 2026-10-15 Claude Code runs a hook in the session's working directory. Notes are read from their files, so one written since the last sync is shown, and redacted before printing. A failure to count sessions or start the sync is one line in the block; the notes are still shown. On a compaction, read from the hook input's `source`, the block opens with one line saying the session compacted and when, so a skill can tell what in its context is a summary.

Built from sections, each with its own budget; each handoff's is the three-line note limit `ele remember` enforces:

- On a `startup` or `clear` source only, every handoff of the project not yet shown and not superseded, ahead of the notes; a lone one is then marked `shown` unless `lone_handoff_pending` is on, several stay pending until closed (see Session handoff)
- On a `startup`, `clear` or `compact` source, the project's active plans, after the handoffs, a lone plan's next item body capped at about 2,000 bytes (see Plans)
- Notes for the current project and owner, plus `global` notes for the owner and `everywhere` notes
- Every open `question` (one no note supersedes), then decisions and facts newest first, capped at ~1.5k tokens (6,000 bytes). Oldest are cut first; questions are cut only when the block would cross 9,500 UTF-16 units, as Claude Code, as of 2026-10-23, shows the model only a 2,000-character preview of hook output past 10,000 characters. Decisions and facts go first, then questions oldest first, and the closing line counts the questions cut and names `ele context`
- Each note line shows its session id prefix when the note has one
- A closing line: older notes not shown, older questions not shown, invalid notes skipped, sessions indexed for the project, and how to search
- After it, when a shown note has a session: how to open that discussion, `ele show --note <id>`, which opens the note's session at the discussion that produced it (see `ele show --note` under Recall)
- A directory no owner covers gets a line saying so and naming `/ele:setup`, and only the everywhere notes; with none, nothing more

## Recall

- `ele recall <words>` syncs first unless another sync holds the lock, in which case it searches what is already indexed (`--no-sync` skips the sync). It finds entries containing every word; each word is quoted, so FTS5 operators and punctuation are plain text, and a word of punctuation alone is ignored
- Ranking: kind (note, prompt, conversation and heads-up, tool call), then FTS5 relevance, then recency
- Output grouped by session, best match first: session id, date, owner, project, then each match's kind and a ~220-character snippet, a note's id before its snippet. The whole output, every line counted, is capped at 8,000 bytes, about 2k tokens; a session heading is printed only with a match under it. `--limit` (default 20) caps the matches. An unlisted `--owner`, an unknown `--kind`, or `--all` with `--owner` is refused
- Scope: the working directory's owner, or with `--project` the project's owner, found as `ele remember --project` finds it and refused as it refuses. An owner scope also matches everywhere notes. A directory no owner covers is refused with a message naming `--owner` and `--all`
- Filters: `--all`, `--kind`, `--owner`, `--project`, `--since <YYYY-MM-DD|Nd>`. Flags may come before or after the words
- `ele show <session> [--around <text> | --at <time>] [--context <n>]` prints a session's indexed, redacted entries in order, centred on the first entry containing the text, a note only when nothing else in the session matches, or on the first entry at or after the time, such as an event's timestamp or a prefix of one, within the same byte budget. A unique prefix of the session id is enough, found by range so the session index serves it. It is not scoped by owner: naming a session is the explicit ask
- `ele show --note <id> [--context <n>]` opens the session a note records (the exact id, not a prefix) at its discussion. Each of the note's distinctive words is weighted by how rare it is among the entries at or before the note's time, so a word the whole session repeats counts for little; the up to three best-scoring entries that score at least a quarter of the best, and lie more than twice `--context` (one by default) apart, are shown in session order, each in up to 2,000 characters and an equal share of the output's bytes, with `--context` entries either side. When no entry shares a word it ends at the last entry at or before the note and shows twice `--context` before it (eight by default); an untimed note counts up to the end of its local date. It says so when nothing precedes the note, and when output is cut it trims the parts' edges, never the entries they centre on

## Secrets

- The archive is verbatim. Directory `0700`, files `0600`
- A redaction pass runs before text is indexed or printed: known token formats (Anthropic and OpenAI keys, GitHub and GitLab tokens, AWS access key IDs, JWTs, PEM private keys) become `[redacted:<kind>]`, and the value of any `key=value` or `key: value` whose key looks secret, JSON keys included, becomes `[redacted:assignment]`
- Patterns live in one table with tests. A new pattern takes effect on `ele reindex`

## Storage

```text
claude-ephant/
  archive/                  transcripts
  config.json               options: global values and per-owner overrides; ele config
  ele.db                    index, disposable
  forgotten/                notes ele forget moved out of the index, by owner
  mining/
    cache/                  classifications, one <analysis>.jsonl each; classifiers/<hash>.md holds each prompt
  move-notice               Linux only: the data dir move's outcome, until ele session-start shows it
  notes/                    Markdown notes
  owner-map.json            owners, path rules, project entries; by hand or ele owner
  plans/                    closed plans' item names, one <note id>.json each; ele plan done
```

On Linux the data dir is `$XDG_DATA_HOME/claude-ephant/`, a relative `XDG_DATA_HOME` ignored as the XDG spec says, else `~/.local/share/claude-ephant/`. Releases before it used the macOS path on Linux too, so every subcommand first moves that old directory to the new one, once, when the old exists and the new does not: a rename, never a copy, since two stores would diverge. It holds a lock on the new directory's parent, so two first uses at once leave one store, and skips the move while a sync holds the old directory's archive lock, using the old path until a later command, and writes no notice. A command that resolved the old path before another moved it can recreate part of the old directory as it writes, left unused, since the new one exists. A failed rename, such as across filesystems, leaves the old path in use, and every command tries again. Either outcome is written to `move-notice` in the directory now in use, since a hook's stderr reaches no one, and the next `ele session-start` shows it to the user and the model, then removes it; the command that tried the move also prints it to stderr. `ELE_HOME` skips the move. macOS keeps its path: moving it would move every current user's data.

Data never lives in the repo, not even gitignored. `ele backup <dir>` copies `archive/`, `config.json`, `forgotten/`, `mining/`, `notes/`, `owner-map.json`, `plans/` and the database via `VACUUM INTO`, so a restore keeps the names that resolve `blocked:` edges into closed plans. It holds the archive lock, and the mining lock when the cache exists, for the whole copy, leaves out lock files, and refuses a directory that is not empty or lies inside the data directory or a git checkout. It copies `notes/` before `plans/`: `ele plan done` stores a plan's names before closing its note, so a backed-up closed note has whatever names were stored. `ele plan done` writes a closed plan's names to a temporary file and renames it into place, so a backup copying `plans/` meanwhile takes the old file or the new one, never a torn one.

## Configuration

- One file, `config.json` in the data dir, holds every option, so one value covers every profile. Not plugin `userConfig`: as of 2026-10-22 Claude Code exports its values only to hook processes, not to commands Claude runs through the Bash tool, where skills call `ele`, and stores them per profile in `settings.json` under `pluginConfigs`
- Top-level keys are global values; `owners` maps an owner to its overrides, so no option takes that name. A value resolves as the session's owner's override, then the global value, then the option's built-in default; a session no owner covers reads global values
- Options are declared once, in `Options` in `internal/config`, with a kind, a default and a description. A key no option takes is kept on write and ignored on read; `ele config list` names it. A file that does not parse, or a known option of the wrong kind, reads as all defaults, so a broken edit leaves `checkpoint_gate` on; `ele config get` says so on stderr, `ele status` on its Config row and the start block in a line
- CLI: `ele config list|get [--owner <name>]` resolve the owner from the working directory, as recall does; `ele config set|unset [--owner <name>]` change the global value unless `--owner` names a listed owner. `set` and `unset` refuse when `CLAUDECODE` is set, printing the command for the user to run outside the session; as of 2026-10-22 a `!` command at the prompt inherits `CLAUDECODE=1`, so it is refused too. A deterrent, not a lock: Claude can still write `config.json` or clear `CLAUDECODE`, and a hook guarding the file would leave scripts and copies open. What stops a silent bypass is visibility: the start block and `ele status` name an option off its default, and the edit shows in the transcript; `set` refuses an unknown key and a value of the wrong kind. `set` and `unset` refuse a file that does not parse rather than overwrite it
- Hooks read an option with `ele config get <key>`, or in-process when the hook is an `ele` command, and so does any skill that needs one: `ele:recipe` reads `recipe_dir`, `ele:remember` `auto_note_writes`, `ele:wrap` `auto_note_writes` and `recipes`. `ele help` lists the commands. A change applies at the next hook of every open session, with no reload
- The start block carries one line naming each option whose value here differs from its default, and `ele status` a Config row
- Options: `auto_note_writes`, boolean, default false, so no user gets notes written without asking unless they turn it on; `checkpoint_gate`, boolean, default true; `colour`, boolean, default true, off for a client that does not render ANSI; `compact_hint_at`, integer, default 150000, the context tokens from which the Stop hook's size hint shows, 0 turning it off, since a model with a larger window wants another threshold; `lone_handoff_pending`, boolean, default false, on keeping a lone handoff pending as several are, see Session handoff; `notes_ask`, boolean, default true, off keeping the Stop hook from asking for notes while `/ele:remember` still works, since it interrupts every stretch of work; `recipe_dir`, folder, default empty, see Recipes; a folder option takes a path as a path option does, `set` refusing one that is not a folder; `recipes`, boolean, default true, off keeping `/ele:wrap` from offering a recipe while a typed `/ele:recipe` still works; `reminders`, boolean, default true, since a reminder shows only what the user saved; `review_voice`, path, default empty, meaning the shipped voice file, see the review spec
  - Not doing: the start block's notes budget and recall's output budget as options: sized to Claude Code's hook output limit and the model's attention, not to taste
  - Not doing: `ele plan check`'s claim and inbox ages as options: plans are shared, and a per-user age makes the check warn differently per teammate
  - Not doing: the 24-hour stale-sync warning as an option: it reports a broken sync, not a preference

## Status and stats

A misused command (bad flag, missing argument) prints that command's help to stderr and exits 2. A group such as `ele handoff` prints its synopses: to stdout with exit 0 for `--help`, else to stderr with exit 2, naming an unknown subcommand. Only an unknown command, named first, prints every synopsis
- `ele status`: is ele working here, now. Last successful sync and its age, the output of background syncs since it (the plain tail with no stamp or a malformed one), whether a sync holds the lock, the owner and project of the working directory, or that none covers it and the `ele owner` command that maps it, and whether the plugin is enabled in each profile's `settings.json`. Runs are shown whole, newest last; only the newest may be cut, and keeps its header

## Events

Memory stays the only thing ele does until a measurement says otherwise; events and mining exist to evaluate ele's own skills against their history and tune them, a standing process that would otherwise rebuild its inventory from raw transcripts with one-off scripts each time.

`ele events`, in the index, written at sync with no model involved. One row per act the entries do not hold, each with session, owner, project, profile, time and whether a subagent's transcript holds it. Names and attribute strings are redacted as entries are. Automated SDK sessions are left out. Review requests and a block's reply are joins against prompt and conversation entries, not copies.

- `skill`: a `Skill` tool call, named for the skill
- `command`: a typed `/command`, named for it
- `agent`: an `Agent` or `Task` launch, named for its subagent type, with its description, whether it ran in the background, and the reviewer files its prompt names, never the prompt
- `hook-block`: hook feedback, named for the hook event, with the first line of its reason and, from a block with a `Changed:` line, its paths as `changed`; older checkpoint blocks list them under `Tracked, dirty:` and `Untracked, new:`, and the earliest list none
- `compaction`
- `injection`: what reached the model's context from a hook or the skill list, named for the hook (`PostToolUse:Edit`, `SessionStart:startup`) or `skills`, with its size in bytes. A hook's JSON `additionalContext` counts; plain stdout counts only for SessionStart and UserPromptSubmit, the hooks whose plain stdout the model sees (as of 2026-10-16 transcripts record UserPromptSubmit output only as additional context); a `systemMessage` is shown to the user and does not, and neither does a hook's blocking reason, which ele records as a `hook-block`
- `reply`: a main-thread assistant text block, with its length in characters. Duration is not carried
- `tokens`: see Usage report
- `tool-error`: a tool result marked an error, with its first 300 characters and, where longer, up to the last 300 of the rest as `errorTail`, so a chain's failing command, which usually reports last, is not cut off; redacted before either cut, since a cut token no longer matches a pattern. It is named for its call's tool and carries the call's text, found at sync by the line id its result line records: the call's line comes first, so where it is indexed at all it is already there. A result with no such id, or whose call is not indexed, gets neither name nor call. The lookup takes the first call on that line

The session rollup is these events and queries over the index rather than a table of totals, since totals added to at sync would count a transcript archived again from its start twice, and events are keyed against that. Prompts, sessions and tool calls come from the entries already there, keyed the same way.

Attributes added at query time:

- A Bash `tool-error` gets `retried`, whether the first call after it in that transcript repeated its command unchanged: absent until such a call follows, absent when either call's text was cut at 300 characters, and a call from the same response, made before the failure, does not count. Another tool's call text is its target alone, such as an Edit's file, so it gets none
- A main-thread `hook-block` carrying `changed`, the checkpoint hook's, gets `checkpointed`, whether a checkpoint ran after it and before the session's next prompt: a main-thread checkpoint skill call, that prompt being a typed checkpoint command, or one run by hand, read as a main-thread Bash call whose text, cut at 300 characters, holds `ele checkpoint freeze` or `checkpoint-reviewed.sh freeze`, or a main-thread Agent or Task call whose description names a checkpoint, since a long freeze call's text can be cut before the freeze. When a main-thread `reply` event falls before that prompt, the first one's text cut at 300 characters is `reply`, its time `replyAt`, and `disputed` is whether its first 600 characters hold `not a checkpoint`, `n't a checkpoint`, `mid-task`, `read-only`, `no file(s) changed`, `not done`, `isn't done`, `waiting on` or `investigation`, case aside, while no checkpoint ran. With another main-thread hook block within a second, such as ele's notes ask at the same Stop, a first reply of one sentence naming a note is that ask's answer and the second reply before the prompt is read instead; a reply of more than one sentence stays, as does one with no closing punctuation, while a one-sentence reply answering both is skipped. The reply is read through `reply` events, which leave out subagent prose a parent's file can hold. `disputed` misses a refusal worded otherwise and counts a reply echoing the block's own `waiting on` or `investigation`; an Agent call describing a checkpoint it does not run counts as one run, and so does one with no description whose prompt names one
- A main-thread `Stop` `hook-block` whose reason names `ele:remember`, ele's notes ask, gets the work before it and whether a note followed. The work runs from the last of the session's previous notes ask and a proposal as the stop-check hook reads one: a main-thread skill call or typed command of `remember`, `handoff` or `wrap`, bare or with a plugin, or a main-thread Bash call whose text, leading `cd <dir>;` or `cd <dir> &&` aside, starts `ele remember` and an argument; a `cd` line followed by `ele remember` on the next is work to the hook, so it ends nothing. A checkpoint ends nothing either, since the hook keeps unproposed work pending across one, so its own calls fall in the work too. `work` is `edits` for an Edit, Write or NotebookEdit call in it, else `bash` for a Bash call, else `question` for an AskUserQuestion call, else `none`; `subagentEdits` is whether a subagent made an Edit, Write or NotebookEdit call in it, which the hook also counts as work; `skill` names the latest main-thread skill call or typed command since the previous notes ask, so a handoff's own `ele remember` does not hide the handoff. `noted` is whether a main-thread Bash call whose stored text holds `ele remember` and a space anywhere, a grep for it included, `ele remember --help` aside, came after the ask and before the session's next prompt, or the session's end. `notedOnReply` is whether one came after that prompt and before the one after it, or the session's end, unless that prompt is a typed command, such as `/ele:handoff`, which starts the user's own run: a proposal asked in prose is approved by a typed reply, but a reply can also be a new request that writes a note, and no bound tells the two apart, so the two attributes stay separate. `bash` does not apply the hook's read rule, which needs the whole command the stored text cuts, so it counts a Bash call the hook reads as a read and passes over

`--during <skill>` keeps only events inside a run of that skill or command; the flag takes the name bare or with its plugin prefix, and matches either. A run opens at a main-thread `skill` or `command` event of that name and closes at a main-thread one of another name, `/model` and `/clear` included, two hours after its last opening, or the first prompt after its closing call, so a typed approval of fixes inside the run keeps it open. A closing call is a main-thread Bash call whose text, cut at 300 characters, holds `checkpoint-log.sh` or `ele checkpoint log` for checkpoint, or `ele ticket ledger record` for ticket-audit, before the next opening of the same name; a call that only names one, such as a grep for it, counts too. A run with no closing call within two hours closes at its first prompt. A subagent's events fall inside its parent's runs, and its skill calls end none.

`ele events [--during] [--kind] [--name] [--owner] [--project] [--session] [--since] [--limit] [--no-sync]` syncs first, as recall does, then prints the newest 200 matches by default, oldest first, one JSON object per line, with a line on stderr when more matched; `--limit 0` prints all. An event is keyed by its line's id and its place on that line, so a transcript archived again from its start adds no event twice; a `tokens` event is keyed by its message id instead; lines without an id are not deduplicated. While the index is not complete for this version of ele, it says on stderr that the events may be incomplete.

## Mining

A model judgment cannot be rebuilt from the archive, so classifications live in a cache in `mining/cache/`, outside the index.

- Each judgment is stored once per unit, classifier and digest, the classifier being a SHA-256 of its prompt, which is kept beside it so the hash stays readable, and the digest a SHA-256 of the digest file the classifier read. A unit is the session and time of the event that opens it: the `skill` or `command` event for a checkpoint run, the first reviewer launch for a review cycle. A judgment under another classifier, or of a changed digest, is kept beside the first, never replacing it. A checkpoint run's judgment is tagged with its era by its time: `inline` before checkpoint reviews moved into subagents, `subagent` after. Inline-era judgments never reach `/ele:checkpoint-stats`, whose schema has no era and would read them as full-mode runs
- A re-mine classifies only units with no judgment under any classifier in that analysis, less the review cycles a run covers. Re-judging is a separate, explicit request, scoped by naming its units: `ele mine --units <file>` lists the units a JSON Lines file names by `session` and `timestamp`, judged or not and wherever the watermark is, and refuses a file naming a unit that does not exist. Classifying units "whose classifier changed" would re-judge every judged unit the first time a prompt differs by a byte
- A watermark per analysis, in `mining/cache/watermarks.json`, so the next run starts where the last stopped. It never moves back
- `ele mine [--no-sync] <analysis>` prints one JSON object per pending unit past the watermark, oldest first, with owner and project, and for a review cycle its reviewer and re-review launch counts; it says on stderr how many units before the watermark have no judgment, so a unit archived late is counted rather than silently skipped
- Review cycles are rebuilt from `agent` events naming reviewer files: main-thread launches in one session at most 5 minutes after the last launch that is not a re-review; a launch whose description reads as a re-review joins the open cycle, or opens one if none is. A checkpoint run after a cycle's last launch closes it, to fresh launches however soon as well as to re-reviews, and a cycle opened on a re-review takes only re-reviews, so a run whose fix pass is re-reviewed after it covers that re-review rather than the next fresh cycle
- Cover: the first review cycle starting at or after a subagent-era checkpoint run in its session, and less than 30 minutes later, belongs to that run and is skipped though it has no judgment. The cache holds no record of the cover, so `ele mine` applies the rule itself
- Digests: `ele mine --digests <dir>` writes one text file per pending unit, named for its session and time, and adds its path to the unit's line as `digest`. A digest is read from the archived transcript holding the unit's opening event and from its subagents' transcripts, found by the agent id in each launch's tool result, since the archive keeps no `meta.json`. In a digest, a human message, or the user speaking, is a user line the user typed: not a tool result, harness text such as a hook's feedback or a task notice, or a compaction summary, which only its `isCompactSummary` flag tells apart. A run's next human messages are read from where its window ends, a failed launch shows its error, and header keys are camelCase. Transcript text is redacted before it is cut, so a cut cannot leave half a secret the patterns no longer match
  - A run's window opens at its invocation, the call or typed command itself where another line, such as an attachment, shares its time, and closes at the next one, named `checkpoint` or `ele:checkpoint` exactly so a typed `/ele:checkpoint-stats` is not one, its session's next review cycle after the one it covers, four hours on, or its report: a later checkpoint can run on the skill already loaded, with no invocation of its own, and is a review cycle of its own
  - A review cycle's window opens at the last human message before its first launch or the first line 15 minutes back, whichever is nearer, and closes at its session's next cycle, three hours on, or its report
  - A report is the last text before the user next speaks in the turn that first runs the record or log command (`checkpoint-reviewed.sh record`, `checkpoint-log.sh`, `ele checkpoint record` or `ele checkpoint log` at a command's start, not merely named); with neither, it is the last text carrying the skill's bold reviewer labels. It is looked for only after every reviewer launched in that window has handed back, by its tool result or, for a background launch, a notice naming its tool-use or agent id; text before that is progress. With a reviewer whose hand-back never appears, the unit has no report and its window runs to its other limits
- Judgments: `ele mine --judgments <file> --prompt <file> --digests <dir> <analysis>` stores one judgment per JSON line, each naming its unit by `session` and `timestamp`, the whole line kept as the result, under the SHA-256 of the prompt, which it saves beside the cache. A line naming no unit of that analysis, or a unit an earlier line names, refuses the file, storing nothing. Every judgment carries the SHA-256 of its unit's digest file, read from the `--digests` directory the listing wrote it to rather than rebuilt, since a sync between listing and storing can move a live session's window, so a re-judge of a changed digest under an unchanged prompt is stored rather than skipped. A unit with no file there refuses the store. The watermark then rises to the newest unit before the first one past it still unjudged, so a unit the pass missed stays listed rather than falling behind the watermark
- The `/ele:mine` skill lists each analysis with digests, classifies them in batches of up to five, one background subagent per batch, and stores the batches' output with `--judgments`. Its two prompts are files beside it, `classify-checkpoint-runs.md` and `classify-review-cycles.md`, keyed by the digest's session and timestamp. They name no scratchpad and send the classifier to no file outside them, so a hash covers everything its classifier reads besides the digest. Only the user invokes it
  - Not doing: merging the two prompts into one: stored judgments are keyed by each prompt's hash
- Analyses are `ele` features, run over the user's own archive and cache, never scripts or run data kept in the repository: run data holds transcript excerpts, and a script written against one run's layout is not rerun
  - Not doing: a mined per-user baseline: a user's checkpoint log runs from install, so a baseline would duplicate it, and `--report` already reads the cache, pre-log runs included
- Figures: `ele mine --report [--no-sync]` reads both analyses' caches and takes the last stored judgment per unit, a re-judge being stored after what it replaces. A review cycle starting inside a subagent-era run's window, from the run to its judgment's `report_ts`, is left out, since that judgment covers it: the prompt ends a run's window at its first cycle's report. The subagent era goes through `ele checkpoint stats`' report, each judgment read as a log record, then adds findings by category, re-review findings by kind and by source, raised by more than one reviewer, refuted, re-raised user decisions, and what the user reported after; the inline era reports per-pass counts, categories, mutations and the same after-figures. Verdicts other than the four are not shown, only counted in the refuted share. Refuted findings, mutation-stage findings and gate failures after review are counted, not listed; user-reported problems are listed. Inline-era runs judged only under the subagent-era prompt carry no per-pass counts and are counted as left out of the inline figures
  - Timing: it syncs first, as listing does, to find each judged subagent-era unit's archived transcript, and reads the window its digest reads, ended early at the judgment's `report_ts` where it has one, so a figure and a judgment cover the same lines, and a review cycle's from its first launch, its digest's lead-in being context for the classifier; each transcript is read once, and a unit whose transcript or opening line cannot be read is left untimed, counted in "units timed N of M", rather than failing the report. Per unit: the window, opening to last line; Bash time in the main thread and in subagents, from each call to its result, both inside the window, and the part spent on calls the digest's gate pattern matches; per reviewer launch naming a reviewer file, by role and by round, a re-review being round 2 by the `rereview` pattern on its description and the head of its prompt: its seconds from first line to last, whether it ran a gate, its convention-file reads and its tool calls

## Usage report

`ele usage [--owner] [--project] [--since] [--no-sync]` syncs first, as events does, and reports from transcripts:

- Sessions with a prompt, and prompts, a subagent's brief not counted as a prompt. A window with tool calls or injections but no prompt prints only its counts
- Tool calls by name, MCP tools by their full name, main thread and subagents apart
- Bytes injected by each hook and the skill list, main thread and subagents apart, and about how many tokens per session, main thread and subagents together, at four bytes a token
- Reply characters, in total and per prompt
- Tokens the API reported, main thread and subagents apart, in total and per session: uncached input, cache write, cache read and output, and the share of input read from cache. Stored at sync as `tokens` events, one per message, named for the model, keyed by the message id rather than the line, since a response is written one line per content block, each repeating its usage. A subagent's lines are streaming snapshots whose output count grows, so the largest is kept. A fork's transcript opens with a copy of its parent's message, which stays the main thread's. `ele events --kind tokens --session <id> --limit 0` lists one session's messages, one per line

It breaks out neither profile nor session. Every keep, fix or remove decision about a context tool cites this report, and the checkpoint skill's cost cuts are measured against it, before and after.

## Session handoff

A long session pays for its whole context every turn, at the cache-read rate when cached, so the natural stopping point is the time to start fresh:

- `ele context --size`: the current session's context in tokens (see Notes)
- Note kind `handoff`: the next task and where the work stands; `/clear` then `continue` resumes it
  - The start block shows the project's handoffs not yet shown, in a section of its own ahead of the notes, on a `startup` or `clear` source only, so a resume or compaction elsewhere does not use them up. The notes list leaves handoffs out
  - Each handoff is headed by its id, when it was written (UTC, to the minute; the date alone for a note with no time) and its session prefix when it has one. With several pending, they are listed newest first, bodies in full, and a line after the section, which the user does not see, tells the session to ask the user which to pick up and whether to drop any
  - The section is also shown to the user: with a handoff or an active plan, the hook prints JSON, the whole block as `additionalContext` and the section as `systemMessage`, since plain stdout reaches only the model. Without one it prints plain text
  - A lone handoff is marked when shown: the start block writes a `shown` time into its front matter. With option `lone_handoff_pending` on, a lone one is listed and asked about as several are, headed `1 handoff from ele`, and stays pending until closed, so a session that opens on other work does not use it up; off by default, since a lone handoff is almost always the one picked. Several are marked by `ele handoff close [--owner <name>] [--project <name>] <id>...`, which the session runs for each the user picks or drops; the rest return at the next startup or `/clear`, so a second stream of work is not lost to the choice. It checks every id is a pending handoff of the project before marking any, and owner resolution is `ele remember`'s. Only the `shown` key is rewritten and the file is renamed into place, so the mark survives a rebuild of the index and a hand edit survives the mark. A lone handoff the start block cannot mark is shown at the next startup or `/clear`, and the block says so; a `close` that cannot mark one exits 1, having printed each it did close, and the rest stay pending
  - `ele handoff list [--all] [--owner <name>] [--project <name>]` lists the project's pending handoffs newest first, each body redacted and on one line; `--all` adds closed ones — closed means shown or picked, not done — with their `shown` time and superseded ones with the note that superseded them. `ele handoff reopen [--owner <name>] [--project <name>] <id>...` drops the `shown` key from closed handoffs, checking every id first as `close` does, so the next startup or `/clear` shows them again; it refuses any id that is not a closed, unsuperseded handoff of the project, so a pending or superseded one stays as it is
  - Two sessions starting together may both show it
- Stop hook: above `compact_hint_at` tokens of context, 150k by default, its size hint suggests `/compact` mid-task, else `/ele:handoff` then `/clear`; the user, not the agent, starts the handoff
- `/ele:handoff`: for a `/clear` mid-work, written when the user asks, with no proposal. `/ele:handoff list` runs `ele handoff list --all` and shows pending and closed handoffs apart, changing none

## Reminders

Something to come back to on a date, where a fact note would show from the day it was written:

- Note kind `reminder` with a `due` date or time, saved by `ele remember --kind reminder --due <YYYY-MM-DD[THH:MM]>`, scoped as any note; `/ele:remember` turns a spoken date into one. A due time is local, as a date is, so the two compare as strings: a date sorts before its own times, so one is due from that day's start
- The start block shows each open reminder of the project, the owner's global ones and the everywhere ones, on every startup, `/clear` and compaction whose local time is at or after its due date or time, soonest due first, in a section of its own after the plans and ahead of the notes, also shown to the user as the handoff section is. Not yet due, it shows nowhere in the block. The notes list leaves reminders out
- The section sits outside the notes budget, as questions do: the user asked to see it, its date keeps the count small, and a reminder dropped for space fails silently
- `ele reminder close [--owner <name>] [--project <name>] <id>...` writes a `closed` time, checking every id first as `ele handoff close` does; in a directory no owner covers, `list`, `close` and `reopen` reach only the everywhere reminders, as `ele forget` reaches only everywhere notes there; `ele reminder reopen` removes it; `ele reminder list [--all] [--colour]` lists open ones, due or not, soonest due first, and `--all` adds closed and superseded ones. `--colour` highlights it as the start block's reminders are, a `due` state yellow and a closed or superseded one dimmed, for `! ele reminder list --colour`; without it the list is plain, as ele cannot tell a `!` command from the model's Bash call
- Option `reminders`, default on: off, no reminder shows, nudges included; saving, listing and closing still work
- A nudge is a reminder with `every`, saved by `ele remember --kind reminder --every <interval> [--due <YYYY-MM-DD[THH:MM]>] [--done-file <path>]`, the interval `5m`, `2h`, `7d` or a bare number of days, so a nudge can be tried out without a week's wait. Closing one re-arms it: `due` becomes the close date plus the days for an interval of whole days, else the close time plus the interval rounded up to the minute, so it never shows early, and `closed` stays empty. An interval given in hours or minutes that is whole days, such as `24h`, is days: it re-arms to a date. The due time is local wall-clock time, so in a daylight-saving fall-back hour a sub-day nudge can re-arm to a time already passed and show up to an hour early; accepted, as it is rare and shows early rather than never; `ele forget <id>` drops it. The start block and `ele reminder list` name its interval and mark it `↻`, written into the text both the model and the user get rather than added by highlighting, so it is one string and survives `colour` off
- A nudge's `done-file` is the done mark of something ele does not run, such as a periodic report: its next due date is the later of `due` and the file's last change plus the interval, re-armed as a close is, and a file that cannot be read makes it due at once. The program that does the work needs no change and no note id, as an id written into another repository's script breaks silently when the nudge is saved again

## Recipes

A multi-step procedure the user will run again, kept as a user skill: `ele remember` refuses a note over three lines, and every live note loads each session, so a procedure has no home in notes.

- `/ele:recipe [procedure]` finds one in the session: three or more steps, to be run again, seen to work, and not already a skill, a task target or a documented step of the repository. One a repository's teammates or CI must also run belongs in that repository, so the skill says so instead of proposing it
- It drafts a `SKILL.md` with a kebab-case name, a description carrying the user's trigger words, numbered steps with the commands as they ran, and what is observable when done; no secrets or session ids
- Always asked Write or Skip, whatever `auto_note_writes` says: a skill loads into every session of the profile, heavier than a note. The user handing the exact words and asking to save them is the approval
- Written to `skills/<name>/SKILL.md` in every profile: each `~/.claude` or `~/.claude-*` holding a `projects` folder, the profiles ele archives, and the running profile whatever it holds, as its next session must list the recipe; once per real folder, as one profile's `skills` may link to another's. No option for the running profile alone: a procedure the user runs again is theirs in every profile. A profile added later does not get it. A skill by that name in any profile is never overwritten. With option `recipe_dir` set, the recipe is written once, to `<recipe_dir>/<name>/SKILL.md`, and each profile's `skills/<name>` is a link to it, so a user who keeps skills in one folder, such as a git repository, does not move each by hand; a name already in the folder is never overwritten, and a profile already holding the name keeps it and is named in the report, and a profile whose `skills` is the folder itself gets no link. The link command checks for the folder itself and an existing name before `ln -s`, which onto an existing folder links inside it, and compares the folder by its real path, as the profiles are listed by theirs. The skill reads the option with `ele config get recipe_dir`; an empty line, or an `ele` too old to know it, writes copies as when unset, and the report opens by saying the option was unset or unknown and naming `ele config set recipe_dir <folder>`, preceded by an update of `ele` when it was unknown, since the copy lands outside the folder a user keeps skills in and only the report says so. The skill lists profiles with `find`, not a glob, since zsh, the Bash tool's shell here, aborts a command whose glob matches nothing

A compiled tool that ignores its flags still runs once; nothing short of not running it rules that out. ## Plans

Work through a fixed list of items one session each, with ele carrying the place across `/clear`. Not a tracker: no assignees, and ele writes no tracker tickets, so none rot on a platform; the plan is the source of truth for planning, and ticket-audit audits only tracker maps a team already keeps. Items carry names and blocking edges ele works out: without them an audit found an item no `blocked:` line held back and a wait nothing would end, and reworded items lost their ledger rulings. Borrowed from OpenSpec: a change carries its why and its tasks, and folds into the spec when done. Not borrowed: its CLI, its spec dialect, its archive step. `plugin/reference/plan-practices.md` holds the practices of published planning and spec workflows, OpenSpec, spec-kit, ADR practice and agent planning skills among them, each adopted, proposed to the item that would apply it, rejected with its reason or already done, dated: researched once rather than per plan, since a search per plan costs much and changes little.

- A plan is a Markdown file in the repository whose code it changes, under `.documentation/plans/`, deleted once its last item is done; git history is its archive. A spec, describing what is or will be built, lives under `.documentation/specs/` and outlasts its plans
- ele stores which plans the user is working through, never their items: the file is the list, and its checkboxes the state. ele's own data still never lives in a repository
- Front matter holds stable facts only: `kind: plan`, `created`, and `spec` when the plan implements a spec in the same repository. Nothing derived, such as counts or the next item, is written into the file. A doc already shaped as a plan is adopted by adding the front matter, an empty `## Inbox` and `## Out of scope`, and the closing action, and by naming its checklist's heading `## Actions` if it has another
- Sections: `## Why`, `## Requirements`, `## Context` (established facts, dated), `## Decisions`, `## Actions`, `## Inbox`, `## Out of scope`. `## Requirements` is optional, numbered and in the user's words, written by `new` and `convert` and changed only by the user, since the review loop checks items against it; a plan without it, as one written before it, is reviewed against its Decisions. It is deleted with the plan, the spec then describing what was built. A Context line not verified against the code or data says "not checked". An architectural Decision carries a `rejected: <option>, because …` line for each option it turned down, so an ADR drafted at the close has its considered options. Items under `###` subheadings inside `## Actions` count, in file order. The last action is always to fold each Decision through `/ele:plan-audit close <path>`, then what the plan built, and its out-of-scope lines as a `Not doing:` list in the section the plan implemented, into its spec; with no spec, to propose each out-of-scope line as a `decision` through `/ele:remember`; then to run `ele plan done`, which stores the plan's item names and whether each was ticked, so a cross-plan edge still resolves after the file is deleted and names stay unique; and delete the plan. It cannot be ticked while the inbox holds an item
- An item is a `- [ ]` or `- [x]` line and its indented body. Progress goes in the body as dated lines (`as of <date>: …`, `next: …`), so a session stopping mid-item needs no handoff. A tick carries one line saying what was asserted, at which boundary and at which commit. Each action but the last leads with a short lowercase kebab name, `- [ ] judge-blocks: …`, written once and never changed, unique across active and closed plans: it reads as a name, grep finds it, and the ledger keys on it, so rewording keeps rulings. Each carries a `done when` line saying what will be observable; `ele plan check` warns on an open one without its name or its `done when` and never refuses. The last action carries neither: nothing blocks on it, and its text is its done-when. `blocked:` leads with item names, local or `<plan>/<name>`, a reason optional after a `;`; `after: <date>` holds an item until then. ele works out the frontier from both and flags a blocker done, missing or left unticked by a closed plan; a line with prose before any `;` is no edge and holds the item until removed by hand. No custom checkbox states, since GitLab and GitHub render only `[ ]` and `[x]`
- A plan names no ele note or session: it is shared, and ele's store is not. ele finds related notes by recall on the item's words when it shows an item
- Next item: the first unchecked, unblocked item under `## Actions`, in file order; the session confirms it or takes the user's pick. With every open item blocked there is none, and `show` says so. Previous: the most recently ticked, from git, an uncommitted tick first, else the newest commit flipping a box in the file; left out outside git and before the first commit
- `## Inbox` takes work captured mid-session, each item dated with where it came from. Next never reads it
- `## Out of scope` holds what inbox triage ruled out, one line each: `- <gist>: <why> (ruled <date>, from <source>)`. A ruled-out item returns only if the plan's why is redrawn: a dropped item that left no record could come back as new work. The binary neither counts nor shows it, and its lines are not inbox items
- Work past a plan's why leaves it at once as a `question` note starting `Plan candidate:`; no section of the plan holds it, so nothing past the why blocks a close. No "not yet specified" section, as wayfinder's map has: the inbox also holds work not sharp enough to be an item
- `plan` is a note kind beside those under Notes: project-scoped only, its body the plan's path from the git root, and left out of the notes list and `ele context`'s notes, as handoffs are
- `ele plan start <path>` writes a `plan` note; it refuses a file without `kind: plan` and a checkbox under `## Actions`, outside the project, already started, or holding an item name another active or closed plan holds. It starts the plan but prints a line naming each plan it could not check for that clash, an active one missing from the checkout, unreadable or not parsing and a closed one whose stored record is missing or does not read, since a silent pass reads as checked; a closed plan at the started path is left off, since it may share its names. `ele plan done` given such a closed plan stores its record from its file or last commit, leaving the plan closed; the line names it by id, since its path may hold an active plan restarted there, which `done` takes first, and `done` refuses a closed plan whose path an active plan holds, since that file holds the active plan's names. A path is taken from the working directory, else from the checkout root where only that names a file, and stored from the checkout root. `ele plan show [<path>]` prints counts (open, blocked, done, inbox), previous, each blocked item's first line with its `blocked:` reasons, and the next item with its line number and body; with no path it shows the project's one active plan, or lists the active plans when there are several, each with its counts and next item's title, and a path need not be started. The active plan missing from the checkout exits 1 naming `ele plan done`. A ticked closing action with items in the inbox gets a line saying to triage them first. `ele plan check [<path>]`, every active plan with no path, lists each warning with its line, exiting 0 on warnings: a blocker done, missing or left unticked by a closed plan, an `after:` date passed, an `as of` line past 14 days outside done items and `## Out of scope`, an inbox item past 7 days from its leading date or undated, an open action but the last with no name or no `done when` line, a name another active or closed plan holds, a line anywhere in the plan citing a note id, a session UUID or an `ele show` of an id that ele resolves (a saved note, an indexed session, or a session whose transcript is on disk though not yet synced, so a commit or a repository's own UUID passes; with the index unreadable every one, so a broken index never silences the check), every action but the last done, and the last ticked while another is open, as OpenSpec's archive warns on unticked tasks; `show` and each plan's summary line count them. `ele plan list [--all]` and `ele plan done <path|id>...` are as `ele handoff list` and `close`. Previous takes the later tick in the file when one diff ticks several, and a box written already ticked was never flipped, so it is never previous. The binary parses and reports; every judgement is in the skill
- `/ele:plan`, invoked only by the user, since a session is not always for the plan; the session never starts plan work unasked:
  - `new` and `convert` settle questions in rounds: each round asks every question whose prerequisites are settled, numbered, with a recommended answer that yes accepts, since a question asked before its prerequisite is settled is asked again; facts are looked up, `ele recall` first, then the code, and the user is asked for decisions and for a fact neither settles; a decision goes in `## Decisions`, with its reason, of each plan that relies on it, and a fact about an item under that item as a dated line; the step that asked them waits until no question is open and the user confirms the whole; a question `convert` leaves as a note is not asked. Written in the skill's own words rather than by calling another plugin's skill, whose names change between versions. Pickup asks each approval as its own question
  - Both ground their rounds first: the repository's ADRs, found by the reference file's rule, an accepted one a settled constraint, so a question it answers is not asked and superseding it is a question of its own; and before each round the facts its questions rest on, recall then the code
  - `new <name>` settles in rounds whatever of the why, the requirements, the items and their design questions the conversation has not, recording each decision already made with its reason; writes a plan from `template.md` beside the skill, which has an empty `## Inbox` and `## Out of scope`, its `## Requirements` from the confirmed rounds; runs the review loop over it; and starts it on approval
  - `convert <spec>` lists the spec's open items with their sections, leaving out those already in a plan and those gated on a measurement or an undecided question, which stay notes, a `question` proposed where none holds one; checks each item's status against the code or data rather than the spec, asking in rounds about what it cannot check and confirming the spec's words each draft quotes as its requirements; writes draft plans, unstarted, grouped by what ships together and split by repository, and runs the review loop over every draft at once, so the drafts and the spec are one corpus, before proposing them; deletes the drafts not approved, all of them on a rejection; applies the user's changes to the rest, re-auditing every remaining draft in plan-audit's Drafts mode where any one's items changed and putting its findings to the user, and starts those in this repository, printing `ele plan start` for another's; removes the spec's own "still to build" prose for the landed plans' items only, in the change that lands them
  - The review loop runs 2 to 3 passes over the drafts before any is shown, each running plan-audit's Drafts mode over every draft and one fresh `ele:plan-reviewer` a draft: a second pass checks the first's revision, as the checkpoint's re-review does, and spec-kit's quality loop caps at 3. Each finding takes a pass-scoped id, `A<pass>.<n>` or `R<pass>.<n>`, and a verdict before any edit, `fixed`, `refuted`, `deliberate` or `open`, with its reason, so a false positive never silently becomes an edit. A later pass's reviewer is briefed with the settled findings by path, each with its id, level and verdict, and re-raises one only with new evidence, keeping its level unless that evidence changes it: reruns of one draft gave one finding major then minor, so an uncarried level could flip the gate on unchanged text. A finding against a requirement is `open`, never an edit to `## Requirements`, since editing one to clear a finding makes the check circular. The loop stops after pass 2 when no blocker or major is `open` and pass 2 fixed no blocker or major, such a fix being unreviewed until pass 3; after the last pass the user sees each finding's id, level, verdict and reason, minors listed without blocking, is asked the `open` ones in a round, and sees a diff of each draft from its first version. Not doing: a cost budget for the loop, since the pass cap bounds it; reviewing a plan amended mid-way, which pickup's premise check and the checkpoint already do
  - with no argument, pickup, made for a return after days away. With several active plans it asks which, listing each with its counts and next item's title. It then checks whether the next item is already done, against the commits and uncommitted changes since the plan's last tick; if so it proposes the tick with an evidence line, writes it on approval, and repeats on the next item until one has no work done. Before any work it shows a task card, the plan, the item's title and body, its blocked reasons and related notes, and asks to start, so a wrong plan is caught before work begins, and the card proposes no edit to the plan. Then: `ele plan show`; recall on the item's words; re-derives each claim the item makes about code with `file:line` or "not checked"; re-reads each blocked item's reasons and proposes removing those now settled; checks that a decision the item relies on lives in one place, and that a status or count it states is dated or derived; triages the inbox with `ele:plan-audit`'s inbox triage options, the one place they are written; writes what it finds under the item as dated lines, and where a finding makes the item's title or a `## Context` line wrong, proposes the reword as its own question with the old text beside the new, writing it on approval and never taking the yes to start as approval for it, a declined one staying a dated line only. A session that compacted mid-item re-reads the item from the file
  - Not doing: parallel worktrees, and grouping several items into one session: they change how a plan runs, and need a plan of their own
- Start block: on `startup`, `clear` and compaction, since a plan is not used up when shown, after the handoffs and ahead of the notes, uncut by the notes budget and shown to the user as a `systemMessage` too. One active plan: the `ele plan show` view, its item body capped at about 2,000 bytes, and a line, which the user does not see, telling the session to ask the user before starting anything. Several: one line each with its counts and next item's title, and the line tells the session to ask whether to work a plan, and which. On compaction the line first tells a session mid-task to carry on, re-reading the plan item if it was one. A plan whose file is missing from the checkout, as on another branch, is named and kept; only `ele plan done` closes one. One that does not parse is named
  - Every `systemMessage` ele writes, the start block's and stop-check's, and the output of `ele reminder list --colour` are highlighted like an editor's view; the session's copy stays plain. Counts: open yellow, blocked red, done green, inbox cyan, a zero dimmed; a warning count yellow. Headers and labels bold; note ids, sessions, commits and dates dimmed, but a reminder's due date yellow and a nudge's ↻ and interval magenta, a colour no other rule uses; commands, `.md` paths and code spans cyan; the `blocked:` label red; a plan missing from the checkout, and a line ele opens with `ele:` or `ele could not` up to its first `;`, yellow. Each span resets only what it set, `\033[39m` or `\033[22m`, never `\033[0m`. Control characters are dropped first, so a plan or note cannot send its own escape sequences; the `colour` option off, or `NO_COLOR` set whatever the option says, leaves the message uncoloured, and `ele reminder list` plain even with `--colour`: one rule for every highlighted output. Claude Code's terminal renders ANSI there, as of 2026-10-17
- A draft plan's review is `ele:plan-reviewer`'s, an agent on `model: opus` with Glob, Grep and Read and no Bash, following `plugin/skills/plan/reviewers/plan.md`, briefed by absolute path only and never seeing the session that wrote the draft, launched by `/ele:plan`'s review loop: an author reads its own draft as confirmation, and the review leans on the model's own knowledge. It reads the draft, its `spec:`, the user's and the repository's `CLAUDE.md`, the repository's ADRs and `plan-practices.md`, and reports a table of each `## Requirements` entry against its items; an ambiguous or untestable requirement, or one naming an implementation, as a question for the user, never an edit, since editing a requirement to clear a finding makes the check circular; an item no requirement asks for, or one reaching past what its requirement scoped; a contradiction with the spec or an accepted ADR; an item breaking a `CLAUDE.md` rule; a done-when line not observable, not achievable, or able to pass while its requirement fails; and practices missing by the reference file or its own knowledge. Code premises, contradictions between items and plans, and `blocked:` edges stay plan-audit's. Each finding carries the line it rests on and a level from the reference file's scale, blocker, major or minor, by effect, the lower when unsure, since a reviewer asked for problems always finds some. The reference file also holds the rule for finding ADRs: `docs/adr`, `.documentation/adr`, `docs/decisions` or the directory `CLAUDE.md` names; only an accepted one binds, one with no status line counting as accepted, since repositories seen write such records once decided, and a partially accepted one for the part its status says is in force; and the next number in each series seen, `NNNN-`, `NNN-` and per-topic `ADR_<TOPIC>_NNN_`. claude-ephant keeps no ADRs: its specs carry each decision's reason. Not doing: `serves:` lines tracing each item to its requirements, since the coverage table does that work
- Whole-plan audit is `ele:plan-audit`'s, a thin skill on ticket-audit's engine, over every active plan by default or the paths given, as one corpus with an item for a ticket. It runs `ele plan check` on each plan first, then ticket-audit's methods across plans, then its own: waits nothing ends, inbox triage across plans (delete, a finding against a decision, move into an action, move to another plan's inbox, a `Plan candidate:` note, out of scope, or leave; pickup triages its own plan's inbox with the same options), `Plan candidate:` notes grouped by theme, a home for each open question note (a plan's inbox, a plan candidate, or staying a question), superseding a note that moves, the newest handoff against the plans, and readiness to close, flagging more than 3 active plans. ele sets no limit on active plans: when four were active, closing them, not starting them, was the struggle, and a refusal at `ele plan start` would push work into notes, where a flag at triage keeps it in view
- `ele:plan-audit`'s Drafts mode, `drafts` with paths, audits unstarted drafts for a review loop, adding every active plan of the repository itself so a caller cannot leave one out, run by `/ele:plan`'s review loop on each pass: `ele plan check`, the corpus and the subagents, then ticket-audit's methods only, premises over the drafts' open actions and the rest across every plan, so a draft contradicting an active plan is found. It reads a draft's `## Requirements` with its Context and Decisions, approves no scope, asks the user nothing, edits no file and writes no ledger record, since the loop that called it puts its questions and owns the revision; each finding takes a level from `plan-practices.md`'s scale and the line it rests on
- `ele:plan-audit`'s Close mode, `close <path>`, sorts each Decision at close, since the deleted plan takes its reasons with it, and a fold of what a plan built leaves out reasons only its Decisions hold. It runs alone, none of the audit's methods with it, and lives in plan-audit rather than `/ele:plan` because only the user can start `/ele:plan`, and a session reaching a closing action any other way must still load the sort. Architectural is hard to reverse, surprising without context and the result of a real trade-off, all three, domain-modeling's test, since an ADR is earned. In a repository keeping ADRs, found by the reference file's rule, it is drafted as the next number in its series, in the format of the series' latest record or its template, status accepted where the series writes one, its `rejected:` lines as the considered options, one ADR a Decision, and written on approval; declined, it folds as design, since declining the record is not declining its reason; in a repository keeping none it folds as design too, so ele never starts an ADR series unasked; one contradicting an accepted ADR asks whether it supersedes it. Design, why what was built behaves as it does, carries its reason into the spec beside that behaviour, writing nothing where the spec already carries it; with no `spec:` it is proposed as a `decision` note. Process, how the plan was run, goes with the plan. The user sees the sort with each fold drafted and approves each. Not doing: archiving a closed plan's text on `ele plan done`, since git is the archive and the fold keeps the reasons; writing an ADR mid-plan rather than at close, since a Decision can still change before the plan closes
- `ele:checkpoint` proposes a tick with its evidence line when a change completes the active item, else a dated progress line, written on approval.
