# Checkpoint and ticket-audit

Two skills in the ele plugin: checkpoint reviews work before it is reported done or committed, and ticket-audit audits a tracker's ticket map against the code. Every script either runs is an `ele checkpoint` or `ele ticket` subcommand.

## Ticket-audit

- Ledger, `logs/ticket-audits.jsonl` in the data dir, `--ledger` overriding it: a record, never a scope. One line per item and text hash: its key, the hash, the newest audit of that text, the methods that reached it and the user's rulings on its findings, each once; a re-audit of unchanged text merges into its line, and changed text starts a new one, since a ruling given the newest hash would read as unchanged. The hash is SHA-1 of the text with its whitespace collapsed, `ticket`'s `itemHash` over `collapseWhitespace`, so changing either after 1.0 reads every recorded item as changed. `record` rewrites the file through a temp file and a rename, so a kill or a full disk leaves the old ledger whole, the temp file written beside the target of a symlinked ledger path, so the link stays a link and its target gets the record; it holds a `.lock` beside that target from reading the ledger to the rename, so two sessions recording at once each keep their lines, whichever path reached the target; an unparsable last line with no newline, cut short by an older append, is skipped with a warning and dropped by the next record, and any other bad line refuses the file, since a skipped line is a hidden ruling. Nothing in it skips a method or hides a finding; a later audit re-raises a ruled finding with the ruling attached, labelled text unchanged or changed since, each ruling printed once, from its unchanged line where one is
  - Key: a ticket's `owner/repo#number`; a plan action's repository, plan path and name, so a reworded action keeps its rulings, the repository being its origin's project path, so a worktree or a clone under another folder keeps them and two repositories in same-named folders keep apart, and the checkout's folder name only with no origin to read. Where the two differ the manifest carries the folder-name key as `alias`, which `rulings` reads and `record` rewrites to the new key, so a ledger from before origin keys keeps its rulings; an unnamed action's or an Inbox item's text, normalised with the marker stripped, so rewording one loses them. Only an action is named, as in `internal/plan`: an Inbox line's leading `word:` or date is not a name, so two lines from one day keep apart; an Inbox line is triaged rather than ruled, so a reword losing its rulings costs little
  - Hash: a ticket's title, body and comments, since §9 records decisions as notes; a plan item's checkbox line and sub-bullets, marker stripped, so a tick is no change
  - `ele ticket corpus` writes `manifest.json` beside the corpus, key, hash and file per item, and takes `--plan <path>`, repeatable, one file per item, `<plan>-<nn>.md`, refusing two plans of one file name. Comments, sub-issues and glab's search stop at 20 pages of 100, a bound on a pagination bug, and warn on reaching it, as gh's 500-hit search does. `ele ticket ledger record` writes at the end of the report, copying the hash from the manifest the audit read, and refuses a key not in it or a method outside §3–§8
  - A ruling on one item's finding goes in the ledger; a decision that would outlive the item is an ele note
  - A ruling that commits the item to an edit not made in this audit is also drafted onto the item, since the builder reads the item, never the ledger: a note on a ticket, a `next:` line in a plan item's body
  - `/ele:ticket-claims` adjudications stay out: "dead" and "still true" are claims about code
- Corpus, `ele ticket corpus`: picks `glab` or `gh` by the origin remote's host, never its path, and prints a remote cut after its last `@`, so no `user:token@` reaches an error even where the URL does not parse, a path holding `@` cut with it; `--clean` removes only the files the earlier manifest lists, and any other `.md` in `--out` refuses the run, kept, since the corpus hash covers every `.md` there; fetches in parallel; warns on a child holding a literal `Part of #MAP`; names no closed child in its `note:` lines; prints a blocker table that ignores prose after "Blocked by"; compares read-backs without the title line and trailing newline, against the body or with `--note` a comment, never both, so a note quoting a body edit cannot pass for it
- `/ele:ticket-claims` (`ele ticket claims`) checks `execution-map` and `typed-as-task`, over up to 500 open tickets or each one numbered, viewed by number so none past the list is dropped; a numbered ticket not open or not readable, and a list at its cap, each draw a warning, a repeated number once, and hold back the all-clear, which would otherwise vouch for tickets never read
- Errors: `plugin/reference/errors.md`, as in Checkpoint's Errors line; ticket-audit adds no rows
- Plans: `ele:plan-audit` audits them on ticket-audit's engine, an item standing for a ticket; ticket-audit keeps tracker maps only. The plan audit and the plan format are claude-ephant's design spec, Plans section

## Checkpoint

- Mode is small or full by size; scope is uncommitted, delta or branch
  - Record keeps a copy of each reviewed file in `~/.claude/cache/checkpoint-reviewed/`, never in the repository's `.git`
  - Record holds the frozen paths alone, hashed as the last freeze saw them, and refuses when any moved since that freeze: dirt off the change list, and an edit after the freeze, were never reviewed, and a record holding them made `check` and the gate call them covered. A path off the change list moving between freeze and record, another session's work, does not refuse it. The refusal asks for a re-review before the next freeze, since freezing again alone would record the edit unreviewed; a run opened before the freeze saved its paths' hashes is refused apart, asking only for a freeze
  - The fingerprint hashes at most 200 dirty paths, bounding the hooks' runtime, and counts those past the cap. A capped state covers nothing: `check` says not covered, the gate weighs the turn's own edited paths beside the moved ones, since a path past the cap has no hash to move, and `freeze` says how many paths went unfingerprinted
  - The fingerprint hashes each path as git stores it: a symlink by its link text, so a retarget or a dangling link moves it, and the record and delta keep and diff the link, not its target's bytes. A path holding a newline or a carriage return, or starting with a quote, is hashed alone, since git's batched hashing would split, truncate or unquote it, and one holding a newline or a leading quote is written quoted, so one such file cannot fail the fingerprint for the whole repository. Before the first commit the dirty paths diff against the empty tree, so staged files count
  - Freeze takes each path literally, never as a glob, and only as git prints it, relative to the root: a directory, `..`, an absolute path or one in another form would never match a frozen path to git's names, and a path outside the root has no fingerprint. It refuses a path holding a newline, which the run's newline-separated path list cannot hold, a repository with no commit yet, which has no HEAD to diff against, and an untracked symlink to a directory, which `git diff --no-index` follows and cannot read; `--no-index` exits 1 for that error as for a change, so its `error:` fails the freeze too. A directory is refused whether the working tree holds it or only the tree does, a submodule's commit entry included, and so is an untracked path under a directory holding `.git`, a submodule or a nested clone, whose untracked files the parent never lists; the refusal names that repository, where the checkpoint belongs. A path the parent tracks there stays the parent's. A path inside the root's own `.git` is refused too, since git never lists one and its diff would be read whole. A bad call, too few positionals, a bare `--base`, an out directory that is not one or no path, prints its reason before the synopsis. Freeze names its files by the root's basename and records the owner in `checkpoint-<repo>.root`, refusing a directory another root of that name froze into; a directory with no `.root`, from before the file existed, is taken over. It builds the diff and delta aside and writes the fingerprint last, so a freeze that fails before those writes leaves the last diff and delta beside their fingerprint, and one that fails among them leaves a fingerprint older than its diff, which sends the re-review check to review again. A git failure fails the freeze, rather than dropping its paths from the diff, and an external diff tool, textconv or colour setting is never used, so reviewers read the bytes `record` hashes, but for a file git's attributes mark binary, which diffs as binary
  - Delta is the freeze's call: whenever a record holds a path on the change list, each path diffs against its reviewed copy, or HEAD where there is none, and the delta's size picks the mode. A repository whose delta is `0 changed` is closed and dropped, and the checkpoint stops only when every repository's is
  - Branch diffs against the merge-base with `@{upstream}`, else `origin/HEAD`, and refuses with neither. Run when asked; offered on a clean tree holding unpushed commits. Writes no delta: no record's copies describe commits
- A run opens with a freeze passing `--start`, or any freeze when none is open, and holds the re-freezes inside it. Each freeze replaces the run's frozen paths, and `--start` resets its clock, so a run abandoned without record or close inside the 120-minute window leaves the next run neither its paths nor its start
- A run's markers, open, frozen paths and start time, are per session and repository, so two sessions checkpointing one repository neither close nor time each other's runs; the record of reviewed bytes stays per repository, since identical bytes were reviewed whichever session asks. A freeze starts a run's clock only with `--start`, when none is running, or when the window has passed since the last freeze, whether or not `record` ended that run, so an idle session's next checkpoint is not timed from its last; `log` or `close` stops it. The window is the full 120 minutes, never rounded up
- Every freeze sweeps what nothing else removes, once untouched for 7 days, far past any run window: an abandoned run's markers and a crashed record's tmp names in the reviewed directory, matched only by ele's own `<sha1>.` names since the directory can be pointed elsewhere, and ended sessions' opt-outs and baselines under the temp directory's `claude-checkpoint/`. A session resumed after a week loses its opt-outs
- Record writes its state, path list and copies through tmp names of its own, so two sessions recording one repository at once never write into each other's, and renames the state last: a copy that does not hash to the record reads as no record, so a crash between the renames never reads as covered. No lock, which a crash would leave behind
- An opt-out refuses a glob with a `.`, `..` or empty segment, one matching an arbitrary probe path, and one matching over half the repository's tracked and untracked paths, so one glob cannot exempt most of the repository from the gate. A glob matching nothing is allowed: an opt-out can come before the file it names
- Errors: one shared `plugin/reference/errors.md` holds the retry rule (quote the error, one fix, one retry that never repeats the call unchanged, none where the row rules a retry out, then stop and report where the caller's instructions put errors) and the general rows, shell and guard-hook errors every skill hits: four per-skill copies had drifted. Checkpoint's SKILL.md keeps a local table of the rows only it hits (`not covered` from `check`, agent type not found, `command not found` in a §2 check); ticket-audit points at the shared file; reviewers read it through the brief's Errors field, since they read only what the brief names, and put an uncleared error under Questions. The guard-hook rows stay general, though only a user with those hooks meets them: a row fires only on its exact error text. No seen counts in the tables: they change nothing the agent does. The rows are drawn from `ele events --during <skill> --kind tool-error`
  - Not doing: a digest of each Bash call's full command, to tell a rerun among commands cut at 300 characters: the tables shipped without it
- SKILL.md size, in both skills: under 500 lines, which the skill lint holds. SKILL.md keeps what every run needs; a case only some runs meet sits in a file under the skill's `references/`, read when it arises: checkpoint's `BRANCH.md`, `DELTA.md`, `HEAD-EXPORT.md` and `PLAN.md`, ticket-audit's `TRACKERS.md`; checkpoint's log field values sit there too, in `LOG.md`, to keep its SKILL.md under 500 lines
- Plans: when a change completes the active ele plan's item, checkpoint proposes its tick with an evidence line saying what was asserted and at which commit; otherwise a dated progress line under the item. Written on approval
- Spec reviewer, `reviewers/spec.md` as `ele:checkpoint-reviewer`, only when the brief quotes a plan item or fetched ticket: a third parallel reviewer in full mode, a file added to the single reviewer's list in small mode. It reports what the item asked that is missing or partial, what is done wrong, and what the diff does unasked, each quoting the item's words, in its own section, unranked against the others. The brief says which requirements the change sets out to deliver, and an Observed field names what was run or measured toward the item, since the diff cannot show it. Its findings go through Verify: a missing requirement outside what the change sets out to deliver is logged `deliberate` and left to the plan's `next:` line, a confirmed unasked change goes to the user rather than being reverted, and any confirmed spec finding left unfixed turns the plan tick into a progress line. A missing requirement falls on no line, so delta scope does not drop it. The re-review gets the quoted item, what the change sets out to deliver and the Observed field
- A test is never changed to pass: the session making the gate green is the likeliest to change one. Verify and Gate fix a red test in the code, and change what a test asserts only for a behaviour change the work sets out to make, which the report names; a rename or signature change edits a test without changing what it asserts, so the rule is on assertions, not on any test edit. `reviewers/bugs.md` reports an expected value rewritten to the code's output, a weakened assertion, a widened tolerance, or a skipped or deleted case with no such behaviour change, so `/ele:review`'s bugs reviewer, reading the same file, reports it too
- A fix to any file a gate check reads, Markdown a skill lint or docs lint reads included, made after the gate's last run started, runs the gate again before the record: a record marks the bytes reviewed, and the gate's last run must have seen them. The bugs reviewer reads the gate's log once it ends, reporting a check failing on a line the change touched, and says so rather than waiting when it has not ended
- Log, `logs/checkpoints.jsonl` in the data dir, `CHECKPOINT_LOG` overriding it. Fields: `mode`, `scope`, `severity` per finding (blocker, defect, quality, nit), `also_raised_by` per finding, so a merged duplicate still counts its reviewers, and `duration` per run, in seconds from the freeze that opened the run to the log line; stats leave a duration of 0 seconds or less out of the median and count it on a line of its own, since a chained freeze and log or clock skew logs one. `/ele:checkpoint-stats` reports each, `ele checkpoint stats --since <YYYY-MM-DD|Nd>` as recall and events take it, from the day's local midnight, 30 days back by default; a bare number of days is refused, since 1.0 freezes `--since` as the one form. Every run is logged, but stats leave out a run whose `repository` is under the temp directory, `/tmp` or `/private/tmp`, the temp directory matched also with symlinks resolved since the line holds git's physical toplevel, and count those left out on a line of their own: a checkpoint run over a fixture in a session scratchpad is a test of the skill, not work. Filtering at read, not skipping at log, keeps the line, so the rule can change later. No `notes` counts: the Stop hook proposes notes, not the checkpoint, so every run logged them 0; `log` accepts one from an older skill and drops it before storing, and stats reads lines with or without it. `ele mine --report` still prints the subagent era's mined notes counts, real before the Stop hook took the ask over, as the baseline for that ask. Review runs share the log with their own scopes, `mr` and `local-branch`, and fields, `target`, `reviewed`, `dropped`, `forge` on an `mr` run, `replaces` on a run logged again after a later finding, the verdict `confirmed`, a per-finding `outcome` and, on a sent finding, `anchor`, and mode `full`, with no `mutations`, `rereview` or `duration`; stats drop the earlier line of the same repository, target and reviewed SHA, so each finding counts once at its latest outcome without matching findings across lines, which carry no id. `log` refuses `target`, `reviewed`, `dropped`, `forge`, `replaces`, `outcome`, `anchor` and `confirmed` on a checkpoint, `forge` on a `local-branch` review, and `mutations` and `rereview` on a review; stats report review runs in their own section, with the skip rate, the dropped counts and sent anchors by forge, kind and answer, since review's severity definitions are wider
- Cost, measured with ele's usage report. Reviews stay in subagents, since inline they would grow the parent's context for every later turn, but cheaper ones:
  - Prose and conventions are one reviewer, reporting under both labels so the Stop hook and the stats sources are unchanged
  - An `ele:checkpoint-reviewer` agent type on sonnet, without the Skill tool, runs it and the re-review; the bugs reviewer and the small-mode reviewer stay on the session's model. As of 2026-10-16 an agent type without the Skill tool receives no skill list
  - Not doing: dropping the `ele recall` fallback from checkpoint §2 and ticket-audit §0: a skill run inside a subagent gets no skill list, so the recall skill they would otherwise point at is not there
  - Small mode up to 40 lines, 100 for Markdown or text. The bar is a judgment, not a measurement

## In the plugin

Checkpoint and ticket-audit ship in the ele plugin: `claude plugin eval` needs a plugin; hooks, scripts, skills and agent type ship and version together; one language. The plugin needs no file outside itself and the ele binary, and names its prerequisites.

- Prerequisites: in the [README](../../README.md). ele on `PATH` is a hard one, since the plugin's hooks call it
- The checkpoint gate, the Stop hook's block and the prompt hook's snapshot, is ele's option `checkpoint_gate`, on by default; with it `false` both hooks only clear the session's baseline, so turning it back on starts from the next prompt, and a `config.json` that does not parse leaves the gate on. Run by hand on a terminal, or with any other character device such as `/dev/null` as stdin, either hook says it reads its hook's JSON on stdin and exits 1, rather than wait on the terminal, and never 2, which from a Stop hook blocks; input that is not JSON passes with 0, as a hook fails open. Claude Code cannot turn off one hook of a plugin
  - Not doing: reading a hook payload past 1 MiB, the limit every ele hook reads to: a prompt pasted past it takes no baseline, so that turn passes the gate
- The gate weighs only what the turn's own calls wrote, since sessions share the working tree and another one's writes move paths too
  - A turn that ran `Edit`, `MultiEdit`, `NotebookEdit` or `Write` on a file in the repository is judged on the moved paths those calls named, and `Changed:` lists only them
  - A turn with no such call is judged on every moved path when a Bash command reads as work by the classifier stop-check uses, since a Bash write names no path, and passes otherwise; so is a turn whose start falls before the transcript tail the hook reads
  - The gate never weighs a path under ele's data directory, which the checkpoint state drops before its path cap: with `ELE_HOME` inside the checkout, every note, index and log write would move a path, and its files would push the repository's own past the cap
  - The paths weighed pass when the latest record holds each at its current bytes, whatever else is dirty
  - The cost: a file a turn writes through Bash beside an edit in the repository goes unchecked, as does a subagent's edit
- A done claim is the final text block's. A printed `git commit` is one, a ready-to-commit claim even mid-item, unless the text offers it for later: "once the suite passes, you can commit". A done phrase is not one on a line counting what is left: "now done; two are left"
- The convention files in the brief are the user's `CLAUDE.md`, under `$CLAUDE_CONFIG_DIR` when set, else `~/.claude`, with what it imports or says to read, and the repository's; the prose reviewer's per-comment tests apply where those hold no comment rules
- In the plugin: the `checkpoint` skill with its reviewer files, the `ticket-audit` skill, the `checkpoint-reviewer` agent, addressed as `ele:checkpoint-reviewer`, and `/ele:checkpoint-stats` and `/ele:ticket-claims` in `commands/`
- Subcommands, grouped as `plan`, `owner` and `handoff` are: `ele checkpoint base|check|close|density|freeze|hash|log|optout|record|stats`, `ele checkpoint gate` (Stop) and `ele checkpoint snapshot` (UserPromptSubmit), and `ele ticket claims|corpus|ledger`; shared state and hook logging are code in `internal/checkpoint`
- The Stop hook's block reads "no checkpoint was reported" word for word, since mining and hook-log readers match it, and names `ele:checkpoint` and `ele checkpoint optout`. It goes out as `hookSpecificOutput.additionalContext`, as stop-check's does, worded as facts rather than orders, which Claude can read as a prompt injection. As of 2026-11-04 on 2.1.308 the terminal showed stop-check's ask as `Stop hook feedback`, not a hook error; the gate's own block not yet seen. Its `Changed:` line lists the paths space-separated, since `ele events --kind hook-block` reads them as `changed` and judges each block by them, with `checkpointed`, `reply` and `disputed`, as design.md's Events section says; `ele show <session> --at <time>` opens a block's turn. ele writes its own hook-log lines, to `~/.claude/logs/hooks-<YYYY-MM>.log` in the format the user's other hooks write, so the plugin depends on no file outside itself
- Contract kept: log formats, and the `reviewers/<name>.md` layout ele's mining reads. Mining matches runs by the old bare names as well as the `ele:` ones, since transcripts from before the skills moved into the plugin keep the old names; the Stop gate and stop-check accept the bare `checkpoint` name too, for a session resumed from before the move
- `task eval` runs the plugin's `claude plugin eval` cases, `plugin/evals/`, against the installed plugin or a path
